# yesh: читаемый язык DevOps-автоматизации

## Зачем

yesh предназначен для небольших операционных скриптов: перезапустить сервис,
развернуть сборку, проверить несколько хостов, сделать backup. Скрипт должен
быть понятен администратору, который знает Linux-команды, но не обязан знать
исторические особенности Bash.

yesh — это язык и интерпретатор автоматизации, а не интерактивная оболочка.
Он сохраняет естественную для Linux форму вызова команд, но не пытается
исполнять синтаксис Bash и не предоставляет shell prompt.

Главный тест языка:

> Можно ли понять чужой скрипт сверху вниз, не мысленно исполняя Bash?

## Три правила языка

yesh не должен требовать от автора постоянной защиты от самого языка.

1. **Одна конструкция — одна семантика.** Поведение не меняется из-за
   синтаксического контекста или случайного способа записи.
2. **Никаких неявных преобразований.** Строка остаётся строкой, список —
   списком, а аргумент команды — одним аргументом. Значения не превращаются
   в код и не проходят неявный word splitting.
3. **Ошибки явны и предсказуемы.** Автору не нужно помнить исключения из
   `set -e` или выяснять, какая стадия pipeline случайно определила итоговый
   код возврата.

yesh не обязан воспроизводить все возможности Bash. Многие из них являются
историческими компромиссами, а не хорошими основаниями для нового языка.

Хороший yesh-скрипт должен оставаться понятным через полгода: автор открывает
его и сразу видит намерение, не вспоминая набор хитростей, необходимых для
того, чтобы скрипт когда-то заработал.

## Базовый пример

```yesh
hosts = [web-1, web-2]
service = nginx

for host in $hosts:
    echo "checking host" $host
    ssh $host systemctl is-active $service
```

Здесь `hosts` — список, `service` — строка, а `ssh` и `systemctl` — обычные
внешние Linux-команды. Внутри runtime аргументы должны оставаться отдельными
значениями, а не собираться в строку для повторного shell-разбора.

## Читаемость как ограничение

- конструкция должна иметь один очевидный смысл;
- значение не меняет тип из-за кавычек или пробелов;
- ошибка указывает на строку yesh, команду и stderr;
- для типичного случая не нужны `$`, `[[ ]]`, `-eq` и `set -euo pipefail`;
- сокращение текста не оправдывает скрытую семантику;
- пример в документации важнее полного списка возможностей.

## Сервисы

```yesh
services = [api, worker]

for service in $services:
    systemctl restart $service
    if systemctl is-active $service:
        echo $service "is running"
    else:
        echo $service "failed to start"
        exit 1
```

Команда в условии проверяет свой exit status. Не требуется отдельный `test`,
обратное сравнение с `$?` или ручное включение строгого режима.

## Планирование изменений

Административный скрипт должен поддерживать режим просмотра действий:

```text
yesh deploy.yesh --plan
```

В этом режиме yesh показывает команды и изменения, но не запускает опасные
операции. Это не должно быть магией: runtime получает режим `plan` и явно
решает, какие операции можно симулировать.

## Ошибки

Команда с ненулевым exit status останавливает выполнение по умолчанию.
Исключения должны быть явными:

```yesh
if systemctl restart api:
    echo "api restarted"
else:
    echo "api restart failed"
    exit 1
```

Ошибка должна содержать источник:

```text
deploy.yesh:8: command failed (5)
  systemctl restart api
  stderr: Unit api.service not found
```

## Секреты и SSH

yesh не хранит SSH-приватные ключи и пароли в исходном коде. Для обычного
запуска используется уже настроенный OpenSSH:

```yesh
host = web-1
ssh $host systemctl restart api
```

Ключи остаются в `ssh-agent` или выбираются через обычный `~/.ssh/config`.
OpenSSH `ssh-agent` предназначен именно для хранения ключей в памяти и
подписания запросов без передачи приватного ключа удалённой машине.

Для CI и production предпочтительны короткоживущие credentials: временный
агент, SSH-сертификат, Vault или другой секрет-менеджер. yesh должен уметь
получать секрет через адаптер, но не обязан сам реализовывать криптографическое
хранилище.

Минимальная модель для будущего:

```yesh
token = secret.env("DEPLOY_TOKEN")
deploy service with token
```

Значение типа `Secret` нельзя неявно вывести через `echo`, включить в обычную
строку, показать в ошибке или напечатать в `--plan`. Его можно передать только
в разрешённое место: stdin, environment конкретного процесса или временный
файл с контролируемыми правами.

Запрещённые практики:

- секреты в `.yesh`-файлах и аргументах команд;
- пароли в URL и строках `ssh`;
- запись секретов в обычный лог или traceback;
- автоматическое чтение всех переменных окружения;
- собственная криптография вместо Vault, SOPS, OS keychain или OpenSSH.

В `--plan` секреты заменяются на `<secret>` и никогда не раскрываются.

## Повышение прав

В MVP `sudo` остаётся обычной внешней командой:

```yesh
sudo systemctl restart api
```

yesh не повышает права автоматически и не добавляет `sudo` скрыто. Из исходника
должно быть видно, какая операция требует root.

Редиректы также не получают магического повышения прав. Для записи в root-файл
нужно использовать механизм самой команды:

```yesh
echo value | sudo tee /etc/myapp/value
```

`sudo` обычно создаёт минимальное окружение и может удалить credentials. yesh не
должен автоматически использовать `sudo -E`; нужное окружение разрешается
явно политикой sudoers. В будущем неинтерактивный режим будет использовать
`sudo -n`, чтобы скрипт не зависал на запросе пароля.

## Реализация

Целевой runtime пишется на Go. Go подходит для yesh по практическим причинам:

- собирается в один исполняемый файл;
- стандартный `os/exec` запускает команды без неявного системного shell;
- `Cmd` поддерживает отдельные аргументы, stdin/stdout/stderr, pipes, context и
  exit errors;
- удобно собирать версии для Linux, macOS и Windows;
- язык достаточно простой для небольшого runtime и CLI-инструмента.

Go является единственной реализацией runtime. Язык yesh не зависит от Python.

```text
text → lexer/parser → AST → semantic checks → runtime → OS processes
```

Runtime отвечает за:

- запуск процесса с массивом аргументов;
- pipeline и редиректы;
- рабочий каталог и окружение;
- exit status всех стадий pipeline;
- timeout, планирование и диагностический вывод.

Внешние команды не исполняются через повторную передачу строки Bash. `cd`,
переменные окружения и другие операции, меняющие состояние самого yesh,
реализуются встроенно.

## Пока не добавляем

- классы и обязательную объектную модель;
- Python-выражения внутри языка;
- автоматическое превращение stdout в структурированные объекты;
- широкую Bash-совместимость;
- декларативную систему уровня Ansible;
- возможности, для которых нет хорошего реального примера.

Открытые вопросы фиксируются отдельно, а не решаются случайно в парсере.

## Запрещённые конструкции по умолчанию

Безопасность — часть языка, а не памятка для пользователя.

- нет `while` без явного лимита итераций;
- `for` перебирает только конечный список, не stdout команды;
- запрещены фоновые команды и `&`;
- запрещены незавершённые pipeline (`command |` и `| command`);
- запрещены вложенные shell-интерпретаторы через `sh -c`, `bash -c` и аналоги;
- запрещены `eval`, command substitution и неявное выполнение текста как кода;
- каждый процесс имеет timeout;
- число итераций ограничено runtime;
- pipe создаётся только между двумя существующими стадиями;
- ошибка не теряется, даже если команда находится внутри pipeline.

Для опасных действий позже может появиться отдельный явный режим `unsafe`, но
обычный yesh-скрипт не должен незаметно превращаться в Bash внутри yesh.
