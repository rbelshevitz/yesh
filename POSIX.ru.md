# POSIX-нюансы среды выполнения

yesh сохраняет Unix-модель процессов, но не обязан копировать все правила
оболочки POSIX. Отличия должны быть сознательными и описанными.

Этот документ описывает текущий контракт POSIX/Linux и границы доказанного
поведения. В полном наборе репозитория сейчас более 200 тестовых функций
(214 на момент подготовки выпуска) и четыре теста с генерацией входных данных
(fuzz). Ниже указано, что именно они проверяют; это не обещание для любого ядра,
дистрибутива или внешней утилиты.

## Конвейеры

Каждая стадия конвейера — отдельный процесс. Среда выполнения должна создать и
соединить канал между соседними стадиями, закрыть в родителе лишние концы после
запуска,
дождаться всех стадий и сохранить результат каждой стадии.

Если лишний процесс держит конец записи открытым, читатель никогда не увидит
EOF. Если читатель завершился, процесс записи может получить `SIGPIPE`/`EPIPE`;
это нормальная часть конвейера Unix, а не обязательно ошибка самого yesh.
[Linux pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html)

Оболочка POSIX обычно возвращает код завершения последней команды конвейера.
yesh намеренно выбирает более безопасное поведение: конвейер успешен только
если успешны все стадии. Это аналог `pipefail`, но встроенный и не отключаемый
флагом.

## Ограничение времени и завершение

Ограничение времени одной команды недостаточно для конвейера: убийство одного
процесса может оставить его дочерние процессы работать. На POSIX все стадии
задания должны получать общую
группу процессов; при отмене среда выполнения посылает сигнал группе, затем
дожидается всех дочерних процессов и через короткий период ожидания использует
`SIGKILL`. Группа настраивается последовательно: первая реально запущенная
стадия становится лидером, следующие присоединяются к её PGID. Нельзя назначать
PGID всем стадиям до запуска первой.

Отмена имеет два уровня: `SIGTERM` сразу после ограничения времени или отмены и
`SIGKILL` после периода ожидания. Эскалация живёт только во время команды и
закрывается при любом пути возврата, чтобы логика безопасности сама не создавала
утечку горутин.

Группы процессов также нужны, чтобы Ctrl-C попадал во весь конвейер переднего
плана, а не только в одну стадию. [Linux process groups](https://man7.org/linux/man-pages/man7/credentials.7.html)

## TTY и управление заданиями

Для файловых DevOps-скриптов достаточно наследовать stdin/stdout/stderr.
Полноценная интерактивная оболочка дополнительно требует управляющего терминала,
группу переднего плана, сигналы `SIGINT`/`SIGTSTP`/`SIGCONT`/`SIGWINCH`,
остановку заданий и PTY для программ, меняющих поведение без терминала.

Это отдельный этап. До его реализации yesh не обещает Bash-совместимое
поведение `fg`, `bg` и Ctrl-Z.

## Перенаправления

Перенаправление — часть абстрактного синтаксического дерева (AST), а не
текстовая вставка. Среда выполнения явно определяет, кто открывает файл, с
какими флагами и режимом доступа, в каком порядке применяются
stdin/stdout/stderr, кто получает ошибку открытия и когда закрывается
дескриптор.

Нельзя автоматически делать перенаправление привилегированным из-за `sudo` в
команде. `sudo command > file` и `echo data | sudo tee file` — разные операции.

## Коды завершения и сигналы

Результат процесса хранит как минимум:

```text
started
exit_code
signal
timed_out
stderr
duration
```

Нельзя превращать убийство сигналом в обычный exit code без потери информации.

## Окружение и поиск исполняемой команды

Окружение передаётся явно и не должно случайно смешиваться с переменными yesh.
`SSH_AUTH_SOCK`, `PATH`, `HOME` и `TERM` имеют операционный смысл; `sudo` может
удалить часть из них своей политикой.

Внешняя команда запускается как `argv`, без системной оболочки, подстановки
шаблонов и неявного разделения слов. Политика контролируемых `PATH` и окружения для
привилегированного запуска ещё относится к работе до стабильного выпуска.
Нельзя считать сам поиск команды доказательством безопасности или позволять
неожиданному `./program` незаметно подменять проверенную команду.

Не следует считать секреты автоматически скрытыми: значение, переданное как
аргумент, может попасть в `argv`, `--plan` может показать раскрытый аргумент,
а ошибка внешней команды — в ограниченный `stderr`. Секреты нужно хранить во
внешнем хранилище или агенте SSH и не помещать в сценарии, которые планируются
или журналируются.

### Как пользоваться агентом SSH

Эти команды нужно выполнять в терминале, из которого запускается yesh, а не
внутри yesh-сценария:

```bash
eval "$(ssh-agent -s)"
ssh-add -t 1h ~/.ssh/id_ed25519
ssh-add -l
```

Перед загрузкой закрытого ключа проверьте, что каталог `.ssh` и сам ключ
принадлежат пользователю, который запускает yesh, а ключ не читается группой
или другими пользователями:

```bash
stat -c '%A %U:%G %n' ~/.ssh ~/.ssh/id_ed25519
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
```

Не выполняйте рекурсивный `chown`, пока отдельно не проверены точный путь и
владелец. OpenSSH может проигнорировать закрытый ключ, доступный другим
пользователям. Агент не делает неправильно принадлежащий или раскрытый файл
безопасным.

`ssh-agent` хранит в памяти закрытые ключи клиента. `ssh-add` загружает ключ
после ввода его парольной фразы, а `ssh-add -l` показывает отпечатки ключей,
которые сейчас находятся в этом агенте. Агент выбирается через
`SSH_AUTH_SOCK`; запуск второго агента в другом терминале не добавляет ключи в
первый. Если `SSH_AUTH_SOCK` уже предоставлен графической средой или WSL,
нужно использовать этот агент, а не запускать ещё один.

Защищайте сокет агента: root или другой процесс того же пользователя может
использовать его для запроса подписей. Не включайте пересылку агента через
`ssh -A`, если промежуточному узлу нельзя доверять или дополнительный переход
не нужен.

Проверить соединение без интерактивного запроса и принимать только заранее
проверенный ключ узла можно так:

```bash
ssh -o BatchMode=yes \
    -o ConnectTimeout=5 \
    -o StrictHostKeyChecking=yes \
    -p 22 user@host true
```

`scp`, запущенный в том же окружении, использует тот же агент. yesh не читает
закрытый ключ и не управляет агентом: он передаёт явные аргументы внешней
программе SSH/SCP. `--plan` может показать эти аргументы, но не доказывает, что
агент, ключ узла, сеть или удалённая учётная запись будут доступны при запуске.
См. [руководство OpenSSH `ssh-agent(1)`](https://man.openbsd.org/ssh-agent.1)
и [руководство `ssh-add(1)`](https://man.openbsd.org/man1/ssh-add.1).

## Что yesh сознательно меняет

- неявное разделение слов отсутствует;
- ошибка конвейера проверяется по всем стадиям;
- бесконечные циклы и фоновые задания запрещены в базовом режиме;
- подстановка команд и вложенная оболочка запрещены;
- yesh не обещает скрывать секреты из `argv` или `stderr`;
- обычный скрипт не требует PTY.

## Что именно покрывает набор проверок

| Слой | Что проверяется | Чего это не доказывает |
| --- | --- | --- |
| разбор и среда выполнения | границы строк и списков, `$name`, условия, циклы, ошибки, `--plan` | правильность смысла любой внешней команды |
| процессы POSIX | конвейеры, `SIGPIPE`, группы процессов, отмена, тайм-аут, ожидание детей, перенаправления | поведение TTY/PTY и произвольного ядра |
| Linux-практика | `rsync`, `rsnapshot`, `systemd`, журнал, `/proc`, хранилища, initramfs, SSH/SCP и наблюдение сети | промышленную эксплуатацию, потерю питания и другую политику безопасности |
| отрицательные пути | отсутствующие входы, неверные идентичности, занятые блокировки, частичный перенос, тайм-аут и отказ службы | восстановление после любого внешнего сбоя |
| тесты с генерацией входных данных | случайные входы для лексера, разбора, раскрытия значений, перенаправлений и среды выполнения | безопасность произвольной программы |

Практические Linux-проверки выполнялись в CI, WSL2, на отдельных Debian- и
Rocky Linux-стендах, а также в loopback/ext4 и изолированной KVM-среде.
Пропуск из-за отсутствующей внешней утилиты не считается успешной проверкой.
