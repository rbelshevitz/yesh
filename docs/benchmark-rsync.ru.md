# Benchmark инкрементального rsync

Это первый полный benchmark корпуса на 100–200 строк для yesh. Поведение
взято из закреплённого MIT-сценария
[`pedroetb/rsync-incremental-backup`](https://github.com/pedroetb/rsync-incremental-backup),
но реализация на yesh пишется независимо.

## Disposable-стенд Rocky

Benchmark запускается без root во временной файловой системе:

```text
fixture/
  source/                  изменяемое дерево входных данных
  snapshots/               опубликованные snapshot-каталоги
  state/                   lock и metadata последнего успеха
  restore/                 новый каталог восстановления
```

В fixture должны быть пробелы в именах, бинарный файл, удалённый файл
источника и оборванная/частичная передача. Реальный mount, UUID/PARTUUID,
заполненный диск и production-подобный SSH — отдельные environment-dependent
проверки.

## Обязательные стадии

1. Проверить source, destination и новый/пустой restore target.
2. Взять эксклюзивный lock на всю операцию.
3. Запустить `rsync` во временный snapshot; `--link-dest` использовать только
   после положительной проверки предыдущего snapshot.
4. Атомарно опубликовать snapshot после успешного rsync.
5. Записать state только после публикации.
6. Применить явный retention и показать удаления в `--plan`.
7. Восстановить выбранный snapshot в новый каталог и сравнить байты.

Негативная матрица: отсутствующий source, неверный previous snapshot, занятый
lock, ошибка rsync, прерванная публикация, повторный запуск и ошибка restore.
После сбоя предыдущий опубликованный snapshot и успешный state должны
сохраниться.

В репозитории уже есть настоящий непривилегированный двухшаговый тест
`TestPOSIXPracticalIncrementalRsyncRoundTrip`. Он запускает пример с
установленным `rsync`, публикует два snapshot, проверяет изменившийся и
неизменившийся файлы и подтверждает, что `--link-dest` переиспользует inode
неизменившегося файла. Также проверяются повторный запуск, отказ при
отсутствующем source и restore через внешний `rsync`. Это рабочая часть
benchmark, а не завершение всей негативной матрицы и retention.

## Что измеряем в yesh

Адаптация должна убрать или явно показать типичные ошибки Bash:

- пути и списки остаются отдельными argv;
- нет неявного `set -e` и неоднозначного статуса pipeline;
- временный результат не принимается за опубликованный snapshot;
- `--plan` показывает source, destination, `--link-dest`, retention и lock.

Также фиксируем оставшуюся внешнюю сложность. В yesh пока нет специальной
области lock на несколько команд, генератора timestamp, API перечисления
каталога и rollback/defer. Новый builtin нельзя добавлять для одной неудачи:
нужен тот же пробел минимум во втором сценарии корпуса. Внешний helper требует
тестов точного argv и отказов.

Текущая гипотеза по дизайну уже, чем отдельный `snapshot` DSL: если benchmark
подтвердит пробел, рассматривать только общие примитивы — например, область
эксклюзивного lock и атомарную публикацию/rename. У обоих должны быть явные
ошибки и применение вне backup (например cron и публикация конфигурации).

`--delay-updates` делает замену отдельных файлов лишь ближе к атомарной; всё
дерево целиком он не публикует. Для whole-snapshot нужен rename завершённого
временного каталога в том же filesystem; финальное имя должно отсутствовать
либо иметь отдельно описанную политику замены. Fixture должен отклонять
существующий final или temporary каталог, а не молча объединять или удалять его.

Профиль durability использует явный `rsync --fsync`, если установленная версия
rsync его поддерживает. Он fsync-ит каждый завершённый файл на receiving side,
но сам по себе не fsync-ит содержащие каталоги и не доказывает сохранность при
потере питания. Более сильная гарантия требует отдельного Linux/filesystem-теста
и не следует из успешного кода процесса.

Успех — не более короткий файл, а возможность быстрее понять переходы состояний
и пути отказа, чем в Bash baseline.

## Цель продукта

Полезный результат — тонкая явная оболочка backup: меньше ошибок в quoting,
lock, публикации и retention, при этом `rsync`/`rsnapshot` остаются видимыми и
отдельно документированными. Будущий helper может упаковать повторяющиеся
preflight и переходы состояния, но обязан показывать в `--plan` source,
target, previous snapshot, retention и destructive actions. Нельзя создавать
второй backup-engine, переизобретать растущий набор ключей утилит или молча
менять семантику rsync/rsnapshot. Специфические ключи утилит остаются обычными
явными argv-аргументами.

## Практики самих утилит

- `rsync --link-dest` запускать в новом пустом snapshot-каталоге. Предыдущий
  snapshot — basis, а не каталог, который нужно обновлять.
- Partial-файлы хранить в закрытом каталоге на destination; не использовать
  общий доступный `/tmp`.
- Считать коды rsync данными. 23/24 означают partial/vanished input, 30/35 —
  timeout; ни один из них не должен публиковать успешный snapshot.
- `--delete` всегда указывать явно. При создании нового snapshot обычно он не
  нужен; удаление старых версий retention — отдельная операция в плане.
- Для rsnapshot перед ротацией запускать `configtest` и test mode; при
  съёмном backup mount задавать `no_create_root=1`, чтобы сбой mount не писал
  в локальный `/mnt`.
- `flock` — advisory-механизм. Нельзя обещать межхостовую сериализацию на
  NFS/SMB без проверки конкретного режима mount; родительский lock-каталог
  должен быть доверенным, поскольку `O_NOFOLLOW` защищает только последний
  компонент пути.

## Профиль совместимости filesystem

Backup-контракт должен явно называть filesystem назначения. `rsync -a`
сохраняет Unix-ориентированные metadata (права, владельцев, symlink, device и
special-файлы) только если destination умеет их представить; FAT/exFAT-подобные
носители имеют другую модель, а ACL/xattr требуют совместимой поддержки с обеих
сторон. Для переносимой копии нужен явный урезанный профиль вроде
`-rlt`/`--no-perms --no-owner --no-group --no-devices`, а поведение для links и
special-файлов следует определить отдельно.

Точность timestamp тоже влияет на корректность. FAT хранит время грубее; rsync
рекомендует `--modify-window=1`. Case-insensitive или Unicode-normalizing
filesystem могут слить разные Linux-имена, а `--delete` при collision способен
привести к потере данных. Такие свойства нужно проверять до destructive run, а
`--delete` не включать в incremental snapshot без явной политики collision.

`--link-dest` зависит от hard links и совпадения сохраняемых атрибутов. Это не
универсальный механизм экономии места: неподдерживаемые типы могут быть
скопированы, а filesystem без hard links для обычных файлов теряет deduplication.
Previous snapshot и новый temporary snapshot должны находиться на одной
доверенной filesystem; отказ link — это результат профиля, а не доказательство
полной эквивалентности snapshot.
