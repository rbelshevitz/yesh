# Права, владельцы и доступ

Сейчас `chmod`, `chown`, `chgrp`, `stat`, `getfacl` и другие утилиты вызываются
как внешние команды, если установлены. У yesh нет собственного механизма
привилегий или управления ACL. Ничего не повышает права через sudo автоматически.

## Работающий пример

Для существующего файла, которым владеет пользователь:

```yesh
config = /srv/app/config.ini
chmod 0640 config
```

Сравнение с Bash:

```bash
set -euo pipefail
config=/srv/app/config.ini
chmod 0640 "$config"
```

Правило текущего интерфейса: внешняя команда получает отдельные аргументы
без разбиения строки по пробелам, но сохраняет собственную семантику прав,
ссылок, рекурсии и привилегий. Символьная форма `u=rw,g=r,o=` тоже остаётся
обычным аргументом внешнего chmod, а не грамматикой yesh.

Ошибка `chmod invalid-mode config` останавливает скрипт. Неверный путь,
EPERM и read-only filesystem не превращаются в автоматический sudo.
`chmod 0640 config` может изменить цель символьной ссылки: проверки
перенаправлений yesh не защищают пути, которые открывает сама команда.

## Что стоит сделать декларативным

Следующий встроенный интерфейс должен описывать желаемое состояние одного
конкретного существующего объекта. Точный синтаксис пока не утверждён.

| Свойство | Требование |
| --- | --- |
| Путь и тип | Явный файл или каталог, без неявного создания родителей |
| Права | Полная восьмеричная запись; разрешённые специальные биты отдельно проверяются |
| Владелец | Проверенное имя с показом UID в плане, либо явно указанный UID |
| Группа | Проверенное имя с показом GID в плане, либо явно указанный GID |
| Область | Один объект; рекурсивный обход — отдельная операция |
| Результат | Было → требуется → изменено/уже соответствует/частичная ошибка |

Если UID/GID/mode уже соответствуют, не вызывать изменение повторно.
Отсутствующее свойство означает «не менять», а не «подставить root».
Неизвестное имя пользователя или группы — ошибка до изменения.
Поле имени не должно молча превращаться в числовой ID из-за его написания.

## Проверка и применение

- Зафиксировать доверенный корневой каталог, проверить компоненты пути,
  открыть объект, получить тип, устройство/inode, владельца, группу, mode
  и число ссылок; показать отличие от требуемого состояния.
- Не следовать символьным ссылкам по умолчанию. Проверки только последнего
  компонента через `O_NOFOLLOW` недостаточно для родительских каталогов.
  Linux-вариант рассматривает `openat2` с ограничением выхода из корня и ссылок;
  переносимый вариант требует обхода через дескрипторы каталогов и чётких
  ограничений при недоступности нужных гарантий.
- Для обычного файла с несколькими жёсткими ссылками отказать: изменение
  inode затрагивает все имена. Число ссылок каталога имеет другую семантику.
- Между планом и применением перепроверить идентичность и исходные атрибуты.
  Выполнять `fchown`/`fchmod` через проверенный дескриптор, а не повторно
  разрешать исходную строку пути. Замена пути после открытия всё ещё
  требует явной политики: дескриптор указывает на исходный inode.
- Владельца/группу менять до окончательных прав; затем проверить фактические
  атрибуты. Несколько системных вызовов не являются атомарной транзакцией:
  частичный успех должен быть виден, без обещания автоматического отката.
- Существующие setuid/setgid, capabilities, расширенные ACL и метки требуют
  отдельного отчёта. Пока сохранение не реализовано, отказывать в изменении
  такого объекта, а не молча сбрасывать или восстанавливать привилегии.
- Рекурсия должна иметь конечный список объектов, ограничения числа/глубины,
  политику перехода точек монтирования и ссылок; не добавлять `-R` автоматически.

`chmod` обычно следует символьной ссылке из командной строки, а GNU chmod
имеет особенности сохранения setuid/setgid каталогов. Поэтому полный
желаемый mode нельзя реализовать простым предположением о флаге `0755`.
[GNU chmod](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html),
[права каталогов](https://www.gnu.org/software/coreutils/manual/html_node/Directory-Setuid-and-Setgid.html).

Смена владельца/группы исполняемого файла может сбрасывать setuid/setgid
и файловые capabilities. У операции есть последствия сверх UID/GID.
[chown(2)](https://man7.org/linux/man-pages/man2/chown.2.html).

ACL связаны с обычными битами mode через маску; `chmod` способен изменить
эффективные права дополнительных пользователей/групп. Наличие mode `0640`
само по себе не описывает всю политику доступа.
[acl(5)](https://man7.org/linux/man-pages/man5/acl.5.html).

Ограничение разрешения пути должно охватывать все компоненты; Linux
`openat2` предоставляет соответствующие флаги, но требует проверки наличия
поддержки ядра и явной обработки ошибок.
[openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html).

## Sticky-bit: общий каталог и чужие записи

Sticky-bit — `01000`; обычный пример общего каталога — `01777`.
В каталоге с sticky-bit удаление или переименование записи дополнительно
проверяет владельца файла и каталога либо соответствующие привилегии.
Одних прав записи в каталог недостаточно, чтобы удалить чужой файл.
Обычные проверки записи и поиска в каталоге при этом никуда не исчезают.

Работающий пример для уже созданного тестового каталога:

```yesh
shared = /srv/app/dropbox
chmod 1777 shared
```

Сравнение с Bash:

```bash
set -euo pipefail
shared=/srv/app/dropbox
chmod 1777 "$shared"
```

Правило: sticky-bit ограничивает удаление и переименование записей общего
каталога, но не запрещает изменение содержимого доступного на запись файла.
Ошибка понимания: mode `0666` у файла не становится защитой содержимого
только потому, что родитель имеет `1777`. И наоборот, владелец файла не может
удалить свою запись без необходимых прав на родительский каталог.

При rename проверяются соответствующие ограничения исходного и целевого
каталогов. Sticky-bit не заменяет setgid: наследование группы новых файлов
задаётся setgid каталога и политикой файловой системы, а не sticky-bit.
Для обычного файла sticky-bit не является современным механизмом защиты;
будущий безопасный интерфейс разрешает его только у каталогов.

В плане показываются и полная запись `01777`, и отдельно `sticky=true`.
Точный желаемый mode обязан сохранять или явно снимать этот бит; нельзя
незаметно отбросить его при преобразовании к обычным `0777`.
Проверка только mode не доказывает запрет удаления: важны UID, владелец
каталога, ACL и привилегии. Испытание с двумя UID отдельно отмечается,
если среда не позволяет запуск от другого пользователя.
Пользователь подтвердил отдельный успешный запуск
`TestPOSIXStickyForeignEntries`: удаление и переименование от второго UID
запрещены, после снятия sticky-bit удаление успешно.
[chmod(2)](https://man7.org/linux/man-pages/man2/chmod.2.html),
[sticky directories](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html).

## Диагностика доступа и ограничения

Перед советом «сделать chmod 777» следует показать, какой доступ требуется,
mode/ACL, владельца, группы процесса, права поиска в родительских каталогах,
флаги монтирования, immutable/append-only, capabilities и доступные сведения
SELinux/AppArmor. Часть сведений может быть недоступна; это отображается явно.
Окончательное решение о доступе принимает ядро, а не наша арифметика mode.

`umask` действует при создании и не заменяет точный mode существующего файла.
Для новых файлов нужен учёт исходного mode, umask и default ACL каталога.
Дескриптор будущего защищённого файла не должен сначала создаваться общедоступным.
Копирование или атомарная замена создаёт новый inode: сохранение прав, ACL,
владельца, xattrs и проверка нового объекта — отдельная часть операции.

`chmod` не меняет NTFS ACL. Под WSL на `/mnt/*` и на сетевых файловых системах
нужно отдельно подтвердить семантику метаданных; результаты тестов временного
Linux-каталога не доказывают её для всех путей.

## Man и проверки

Читайте `chmod(1)`, `chown(1)`, `chgrp(1)`, `chmod(2)`, `chown(2)`,
`path_resolution(7)`, `openat2(2)`, `acl(5)`, `umask(2)`, `capabilities(7)`.
Для внешних утилит сверяйте доступные флаги локальной реализации GNU/BSD.

Текущие тесты изменяют только собственные временные файлы: числовые и
символьные mode, путь с пробелами, неверный mode, chown на уже существующие
UID/GID и создание файла при umask 077. Проверки ссылок у перенаправлений
не считаются тестами будущего интерфейса прав.
В текущем окружении getfacl/setfacl отсутствуют, getcap/lsattr/stat доступны;
ACL, смена владельца на другого пользователя, специальные биты и метки
остаются отдельными испытаниями в изолированном окружении.
