# Хранилища, блочные устройства и fstab

Реализован читающий Linux-срез, описанный ниже. Целевые изменяющие операции
в первом примере пока являются проектом.

Работа с дисками — отдельный safety-контур. Нельзя сводить её к строковой
команде `mount`: ошибка устройства или mountpoint может повредить данные.

## Целевые операции

```yesh
disk = device by uuid "..."
inspect $disk
mount disk at /mnt/backup readonly
require mounted /mnt/backup
unmount /mnt/backup
```

Диагностика должна использовать явные системные источники:

- `blkid` для UUID, PARTUUID, TYPE и LABEL;
- `lsblk` для дерева устройств, mountpoint и read-only состояния;
- `findmnt` для проверки фактической точки монтирования;
- `/etc/fstab` только через структурированное чтение и проверку записи;
- `stat`, `df` и `du` для размера, свободного места и заполнения.

## Анти-мартышка

- нельзя монтировать по `/dev/sdX` без подтверждённой идентичности устройства;
- UUID/PARTUUID должны однозначно разрешаться, иначе операция останавливается;
- mountpoint обязан быть каталогом и не должен быть неожиданно занят;
- перед backup проверяется, что путь действительно находится на нужной FS;
- `require mounted` падает, если mount отсутствует или смонтирован не тот источник;
- запись в `/etc/fstab` не делается автоматически в MVP;
- `umount` и `mount` получают timeout и видимую ошибку busy;
- операции над разделами, `mkfs`, `wipefs`, `dd`, `fdisk` и `parted` запрещены
  встроенным API MVP;
- `--plan` и dry-run не должны притворяться проверкой реального состояния.

## Последовательность безопасного backup

```text
resolve UUID → inspect → verify filesystem → verify mountpoint
→ verify free space → run backup → verify result → report source and target
```

Приоритет — read-only диагностика. Изменяющие операции добавляются только с
отдельным типом действия, preflight-проверками и тестом на неправильный диск.

## Реализованный читающий интерфейс

Перед записью проверяется точная точка монтирования: обычный каталог на
корневой ФС не должен проходить проверку только потому, что смонтирован `/`.

```yesh
backup = device by uuid "replace-with-real-uuid"
inspect $backup
require mounted /mnt/backup from $backup filesystem "ext4"
echo "backup preflight passed"
```

Для сравнения на Bash (yesh дополнительно отклоняет неоднозначную identity):

```bash
set -euo pipefail
source=$(findfs UUID=replace-with-real-uuid)
findmnt --mountpoint /mnt/backup --source "$source" --types ext4 >/dev/null
```

Правило: `device by uuid|partuuid значение` разрешает одну identity, а
`require mounted путь from устройство filesystem тип` требует точного
совпадения каталога, устройства и файловой системы.

`inspect устройство` выводит JSON с PATH, MAJ:MIN, UUID, PARTUUID, FSTYPE,
LABEL и RO из снимка lookup. Идентификаторы сравниваются буквально, с учётом
регистра. Дубликат UUID/PARTUUID среди сообщённых устройств или отсутствие совпадения
останавливает выполнение. Недоступные метаданные не доказывают глобальную
уникальность среди всех устройств. Используются `lsblk` и `findmnt` из util-linux с
явными JSON-полями, пределом выполнения 10 секунд, двухсекундным ожиданием отмены и 4 MiB
вывода каждого потока.
Никакого скрытого sudo или прямого probing устройств нет.

`require mounted` повторно разрешает identity, проверяет major:minor и путь
устройства, отклоняет symlink-компоненты mountpoint, не-каталоги и монтирование
поддерева ФС. Bind mount всей ФС от обычного mount эта проверка не отличает.
Это снимки состояния, а не блокировка от параллельного mount/device change
и не доказательство права будущей записи.

Пример ошибки: `/mnt/backup` существует на корневой ФС, но не смонтирован
отдельно, либо UUID/тип ФС не совпадает — скрипт завершается до backup.

`--plan` показывает отложенные lookup/inspect/require, не запускает утилиты
и не проверяет пути; он не доказывает наличие диска. Device — отдельное
значение, его нельзя передать аргументом внешней команды или превратить в
строку. Mount/umount пока остаются проектом; чтение fstab описано ниже. Политика обычных
внешних команд этим интерфейсом не меняется.

## Чтение fstab (Linux)

```yesh
mounts = fstab "/etc/fstab"
inspect $mounts
echo "fstab snapshot read"
```

Сравнение с Bash:

```bash
findmnt --fstab --json --list --nocanonicalize \
  --output SOURCE,TARGET,FSTYPE,OPTIONS,FREQ,PASSNO
```

Правило: `fstab путь` читает ограниченный снимок обычного файла через libmount
из util-linux; `inspect` показывает записи по порядку и диагностику без применения.
В отличие от отдельного Bash-вызова, сообщение парсера означает ошибку даже
при status 0. Ошибка: повреждённая строка перед правильной записью должна
остановить скрипт, а не превратиться в частичную таблицу. Пустой файл допустим.

Пределы: 4 MiB, 10 000 записей, 64 KiB на строку. Нет разрешения UUID,
канонизации путей, mount helpers или запуска systemd generator. Приватный
временный снимок удаляется после запроса. Plan откладывает чтение.
Опции хранятся цельной строкой: запятые в кавычках и повторные опции нельзя
сортировать или бездумно делить. Inspect показывает только имена опций без
значений; сетевые и прочие нестандартные источники скрыты во избежание вывода
учётных данных. Локальные пути и UUID/PARTUUID/LABEL/PARTLABEL видны.
Дубликаты non-swap target выводятся как диагностика: порядок сохранён,
намерение требует проверки. Несколько swap с target `none` — не дубликаты.

Это конфигурация, не активные mount и не итог зависимостей systemd. `nofail`
разрешает продолжить boot, но не подтверждает готовность backup-диска.
`noauto` не отключает `x-systemd.automount`. Systemd трактует passno как boolean,
с отдельной проверкой root прежде остальных. Неизвестные опции остаются
непрозрачными: успешное чтение не означает проверку успешной загрузки ОС.
Источники: [fstab(5)](https://man7.org/linux/man-pages/man5/fstab.5.html),
[libmount](https://www.kernel.org/pub/linux/utils/util-linux/v2.41/libmount-docs/libmount-Table-of-filesystems.html),
[systemd.mount](https://www.freedesktop.org/software/systemd/man/latest/systemd.mount.html),
[systemd-fstab-generator](https://www.freedesktop.org/software/systemd/man/latest/systemd-fstab-generator.html).

## Проверка записи fstab по устройству и активному mount

```yesh
mounts = fstab "/etc/fstab"
require mounted /mnt/backup from $mounts
echo "configured backup device is mounted"
```

Для сравнения на Bash (необходимы дополнительные проверки неоднозначности):

```bash
findmnt --fstab --mountpoint /mnt/backup --output SOURCE,FSTYPE
findmnt --kernel --mountpoint /mnt/backup --output SOURCE,FSTYPE,MAJ:MIN
```

Правило: `require mounted путь from снимок_fstab` требует единственную запись,
уникальное устройство по UUID/PARTUUID и точный активный mount с совпадающими
устройством и типом ФС. Ошибка: записи нет, их несколько, UUID недоступен,
смонтирована другая ФС или это обычный каталог на `/` — скрипт остановится.

Первый срез проверяет целую локальную ФС с явным типом и источником
UUID/PARTUUID; внешние кавычки идентификатора — кавычки fstab, не код yesh.
Пути/LABEL, swap, auto/список типов, bind/rbind, move/remount, loop и опции
btrfs subvolume отклоняются как пока не поддержанные. Лексически одинаковые
пути (`/backup` и `/backup/`) тоже неоднозначны. Используется загруженный
снимок, а не последующие правки исходного fstab.

Сначала опрашивается таблица mount ядра без канонизации путей, затем проверяется
сам каталог. Один autofs без нужной ФС отклоняется без активации automount.
`noauto`, `nofail` и `x-systemd.automount` не оправдывают отсутствие mount.
Несколько активных mount в одной точке отклоняются: первая запись не выбирается.
Plan откладывает выбор записи, разрешение устройства и фактическую проверку.
Проверяются только точка, устройство и тип ФС: опции mount, доступ для записи,
свободное место, boot и параллельные изменения остаются отдельными проверками.

## Контракт readonly mount (следующий storage-срез)

Текущий `require mounted` намеренно не означает, что backup доступен для записи,
смонтирован только для чтения или имеет достаточный объём. Это отдельные
наблюдения: файловая система может быть `ro`, каталог — доступен, а свободное
место меняется сразу после проверки.

До добавления встроенной storage-операции отдельный привилегированный стенд
должен доказать:

- эффективные options из таблицы mount ядра, а не только options из `/etc/fstab`;
- отдельные требования readonly и writable;
- write probe с уникальным временным файлом в целевой точке, удаляющий только
  свой файл и различающий отказ прав и read-only;
- проверку свободного места через статистику ФС с проверенными двоичными единицами;
- явное ограничение: это preflight-снимок, а не lease и не гарантия для
  последующей операции backup.

Пока такого стенда и отрицательных тестов нет, сценарии должны явно использовать
внешние `findmnt`, `df` и существующую проверку `free_space`. Встроенных `mount`,
`umount`, записи `/etc/fstab` и неявной write probe нет.

Сетевые ФС — отдельный диагностический контур. Локальную проверку UUID/PARTUUID
нельзя переиспользовать для NFS/CIFS. Для `credentials=` yesh в будущем может
проверять только внешний обычный файл, владельца и строгий mode; читать,
печатать или создавать этот файл нельзя. Inline `password=` остаётся ошибкой
для любого будущего интерфейса записи fstab.
