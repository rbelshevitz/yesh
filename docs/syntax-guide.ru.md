# Учебник по синтаксису yesh

💡 Чтобы открыть оглавление, нажмите кнопку с тремя маркерами в правом верхнем
углу.

yesh — небольшой язык для ограниченных Linux-операций, в которых важно заранее
понимать, что будет запущено, что может измениться, как проверить результат и
что произойдёт при ошибке. Для небольших административных задач, где ошибка
может дорого обойтись, yesh делает такое описание проще для чтения и проверки,
чем эквивалентный Bash-сценарий.

Это учебник, а не полный перечень возможностей. Здесь мы напишем несколько
коротких сценариев и по пути разберём правила языка. Для точной справки см.
[справочную страницу языка](../man/yesh-language.7) и
[быстрый старт](quickstart.ru.md).

## Основная идея

yesh не превращает команду в одну строку для оболочки. Он сохраняет имя
программы и каждый аргумент отдельно, а затем напрямую передаёт этот список
внешней программе. В терминологии Unix такой список называется вектором
аргументов (`argv`): первый элемент — имя программы, остальные — её аргументы.

Например:

```yesh
install -m 0640 -- config.next /etc/myapp.conf.next
```

Внешняя программа `install` получает `-m`, `0640`, `--` и два пути как отдельные
аргументы. yesh проверяет раскрытый список и его границы, но не решает, что
означает `install`, и не проверяет наличие нужных полномочий.

### Как yesh разбирает файл

У yesh есть отдельная граница между текстом сценария и его выполнением:

```text
текст → лексический анализатор → parser → AST → исполнитель
→ внешние процессы Linux
```

Сначала лексический анализатор выделяет слова, строки, списки, операторы и
блоки, учитывая кавычки. Затем parser проверяет грамматику и строит внутреннее
дерево (AST).
Только после успешного разбора исполнитель раскрывает значения, строит точный
`argv`, выбирает ветвь условия и запускает внешние процессы.

Из этого следуют четыре правила:

- ошибка синтаксиса останавливает файл до запуска первой команды;
- parser не запускает команды, не читает состояние хоста и не исправляет
  неоднозначный текст молча;
- обычное слово остаётся литералом, а ссылка на переменную пишется явно как
  `$name`;
- `--plan` использует то же разобранное дерево, но вместо запуска показывает
  возможный порядок действий и раскрытые аргументы.

Например, `echo service` и `echo $service` — разные вызовы для parser-а:
первое передаёт слово `service`, второе требует существующую переменную.
Неизвестное имя `$service` — ошибка, а не пустая строка. Навигатор yesh
использует тот же parser: сгенерированный текст нельзя считать годным только
потому, что его собрала форма.

## Экспериментальный навигатор

Навигатор — это экспериментальный полноэкранный текстовый интерфейс для
терминала (TUI). Это помощник для первого знакомства с yesh, а не отдельный
исполнитель команд. Его смысл — помочь новичку получить первый читаемый
сценарий, не запоминая сразу весь синтаксис, и при этом сохранить результат
видимым и объяснимым. Вы выбираете намерение и заполняете форму, навигатор
собирает из неё обычный текстовый файл yesh, а затем передаёт этот текст тому
же parser, который используется при запуске файла из терминала.

TUI пока остаётся экспериментальным. Его планируется вынести из основного
исполняемого файла `yesh` в отдельный необязательный `yesh-navigator`. До
завершения этой переделки сборка с дополнительным тегом остаётся рабочим
артефактом; для запуска сценариев используйте обычную команду `yesh`.

Порядок работы такой:

1. заполнить форму;
2. исправить ошибки, если parser их обнаружил;
3. после успешной проверки открыть `План` и посмотреть команды и порядок
   действий;
4. при необходимости сохранить новый файл сценария;
5. запустить его позже явно из терминала, когда вы сами проверили текст и план.

Кнопка `План` не заменяет разбор. Если текст не прошёл разбор, просмотр плана
и сохранение блокируются: сначала нужно исправить ошибку. Навигатор не
запускает собранный сценарий, не угадывает исправление и не скрывает проверку
состояния системы за формой.

👀 Перед сохранением прочитайте получившийся файл и проверьте пути, имена служб,
права и внешние команды. Успешный разбор означает только, что yesh понял
синтаксис и смог построить план; он не доказывает, что команда безопасна для
конкретного узла или что у вас есть нужные полномочия.

## Для кого этот учебник

Этот учебник — для администратора Linux, который умеет запускать обычные
команды и читать их справку, но не хочет изучать исторические особенности
Bash. Нужно знать, что такое файлы, коды выхода и простые конвейеры.

Первое прохождение займёт примерно 25–35 минут. К концу учебника вы сможете
написать небольшой административный сценарий, проверить его план, объяснить
передаваемые аргументы и предсказать поведение при отказе.

Не обязательно читать все разделы подряд. Для первого занятия достаточно
разделов 1–9, затем можно перейти к разделам 11–13 и полному сценарию.
Раздел 10 и разделы 14–18 удобно оставить для следующего прохода и
использовать как справку при написании собственных сценариев.

## Перед началом

Сначала соберите yesh из корня репозитория:

```text
go build -trimpath -o yesh ./cmd/yesh
```

Для первых упражнений не нужны права администратора, работающий systemd,
сеть или специальное оборудование. Нужны Go для сборки и обычные команды Linux,
которые используются в конкретном примере. Отдельные примеры ниже показывают
проверку службы через `systemctl`; их можно прочитать и проверить в режиме
`--plan`, даже если systemd недоступен.

## Практический маршрут

Учебник лучше проходить как один операционный сценарий, а не как перечень
синтаксических правил:

1. [инкрементальный снимок через `rsync`](benchmark-rsync.ru.md) — временный
   каталог, `--link-dest`, публикация и отказ без замены прошлого снимка;
2. [запуск `rsnapshot`](rsnapshot.ru.md) — `configtest`, пробный режим,
   просмотр ротации и явное подтверждение;
3. [наблюдение службы](systemd.ru.md) — конечный снимок, измерение и сводка;
4. [SSH-ключи](#ssh-ключи-для-источника-на-другом-узле) — без пароля в
   сценарии, с проверкой ключа узла и без отключения доверия;
5. [безопасное развёртывание статического релиза](#безопасное-развёртывание-статического-релиза)
   — публикация, проверка ответа и откат;
6. [проверка перед запуском](#15-проверка-перед-запуском) — план, отказ и
   границы доказанного поведения.

Для каждого практического шага сначала запускайте `--plan`, затем положительный
стенд, затем отрицательный случай. Успех внешней команды доказывает только её
собственный результат; yesh отдельно проверяет, что временный результат можно
публиковать, что прежний снимок не изменился и что наблюдение относится к тому
же запуску службы.

Этот маршрут подтверждает работу на конкретном Linux-стенде. Он не доказывает
сохранность после потери питания, произвольные права, доступность сети или
поведение другой версии systemd и файловой системы.

Комментарии начинаются с `#` и идут до конца строки. Они помогают описать
цель примера и его границы, но не выполняются:

```yesh
# Этот комментарий не запускает команду.
echo ready
```

## 1. Первый сценарий

Сначала напишем сценарий, который только проверяет исходный путь. Создадим
файл `check-source.yesh`:

```yesh
source = "source"

if exists $source:
    echo "source is ready"
else:
    echo "source is missing"
    exit 2
```

Запустим его из каталога, где существует `source`:

```text
./yesh check-source.yesh
```

Сценарий только проверяет, существует ли исходный путь. Если путь существует, он
печатает `source is ready` и завершается успешно. Если пути нет, он печатает
`source is missing` и возвращает код `2`. Сам сценарий ничего не изменяет;
в следующих разделах мы добавим внешнюю команду и публикацию подготовленного
результата.

`exists` проверяет наличие пути сейчас, но не гарантирует, что позже к нему
можно будет обратиться. Отказ в доступе
или цикл ссылок приводит к ошибке, а не к сообщению `source is missing`.
Создайте или уберите путь и проверьте оба результата самостоятельно.

Перед запуском можно посмотреть план:

```text
./yesh --plan check-source.yesh
```

План показывает обе ветви, но не запускает команды и не открывает перенаправления.

## 2. Литерал и переменная

Слово без `$` остаётся текстом:

```yesh
unit = nginx.service

echo unit
echo $unit
echo "$unit"
```

Результат:

```text
unit
nginx.service
$unit
```

Правило: значение переменной раскрывается только через `$name`. Формы
`${name}` и неявное разбиение строки на слова не поддерживаются.

Двойные кавычки в yesh не раскрывают переменные. Поэтому
`"$unit"` — буквальная строка `$unit`. Если нужно передать значение
переменной, пишите `$unit` без кавычек: границы значения уже сохраняются.

Ошибка:

```yesh
unit = nginx.service
echo $missing
```

Неизвестная переменная — ошибка, а не пустая строка.

Проверка: замените `$unit` в последней команде на `unit`, затем снова запустите
пример. Вы должны увидеть буквальное слово `unit`, а не `nginx.service`.

## 3. Строки и списки

Строка остаётся одним значением, список раскрывается в несколько аргументов:

```yesh
message = "backup finished"
hosts = [web-1, web-2]

echo $message
for host in $hosts:
    echo $host
```

Кавычки сохраняют границы значения. Одинарные кавычки сохраняют текст,
двойные допускают экранированные последовательности Go, например `\n` и `\t`.
Запятая внутри кавычек не разделяет элементы списка.

Не нужно писать кавычки вокруг раскрытия переменной ради сохранения границ:
границы значений уже известны языку. Кавычки нужны для самого текста.

## 4. Условия и блоки

Блок начинается после двоеточия и выделяется отступом:

```yesh
config = "/etc/my-service.conf"

if exists $config:
    echo "configuration exists"
else:
    echo "configuration is missing"
    exit 2
```

`exists` — встроенная проверка существования пути. Отсутствующая цель даёт
ложный результат. Отказ в доступе, цикл ссылок и повреждённое значение пути
останавливают сценарий.

Внешняя команда тоже может быть условием:

```yesh
if systemctl is-active --quiet -- nginx.service:
    echo "nginx is active"
else:
    echo "nginx is not active"
    exit 1
```

Обычный ненулевой код внешней команды выбирает `else`. Если yesh не может
запустить команду, получает сигнал отмены или превышает время ожидания, это
ошибка выполнения.

Например, `false` запускается и возвращает ненулевой код, поэтому это обычный
ложный результат:

```yesh
if false:
    echo "not reached"
else:
    echo "the command returned false"
```

А отсутствующая команда не выбирает `else`: yesh не смог выполнить действие и
останавливает сценарий с сообщением об ошибке.

## 5. Цикл с заданным числом повторов

`for` обходит конечный список:

```yesh
services = [nginx.service, sshd.service]

for service in $services:
    systemctl is-active --quiet -- $service
    echo $service "is active"
```

Если проверка одной службы завершается ошибкой, последующие элементы не
обрабатываются. `while` пока не поддерживается: бесконечные и неограниченные
циклы не входят в базовую модель yesh.

Чтобы продолжать после неуспешной проверки службы, поместите команду в `if` и
явно решите, считать ли такой результат допустимым. Сам цикл не скрывает
ошибки и не превращает их в пропуск элемента.

## 6. Конвейеры и перенаправления

Linux-команды остаются видимыми:

```yesh
ps -eo pid=,ppid=,user=,rss=,stat=,comm= | sort -k 4,4nr > processes.txt
```

yesh запускает стадии напрямую и передаёт им точные аргументы. Скрытого
повторного разбора через оболочку нет.

Ошибка любой стадии означает ошибку всего конвейера. Редирект `<` допускается
у первой стадии, `>` и `>>` — у последней. `--plan` показывает раскрытые
аргументы и пути без запуска команд и открытия файлов.

Перед запуском yesh разбирает весь конвейер и проверяет его ограничения. Если
форма конвейера неверна, ни одна стадия не начнётся. Но это не делает выполнение
атомарным: внешняя команда может записать частичный результат и затем завершиться
ошибкой. Поэтому для замены действующего файла или каталога используйте
отдельный временный путь и `publish` только после успешного завершения.

Проверка: замените `>` в примере на неподдерживаемый `2>`. yesh должен
отклонить такой редирект до выполнения первой стадии.

## 7. Явное завершение

```yesh
code = 7
exit $code
echo "эта строка не выполняется"
```

`exit` завершает весь сценарий с десятичным кодом от `0` до `255`. Это
встроенное завершение yesh, а не внешняя команда и не стадия конвейера.

## 8. Точные аргументы внешних команд

Обычное слово передаётся как текст, переменная раскрывается явно, а список
даёт несколько отдельных аргументов:

```yesh
unit = nginx.service
options = [--quiet, --, $unit]

systemctl is-active $options
```

Это передаёт `systemctl` три отдельных аргумента после имени команды. Значение
переменной не разбирается повторно как yesh-код или как строка оболочки.

Такой список часто называют вектором аргументов, или `argv`: первый элемент —
имя программы, остальные — её отдельные аргументы. Это не одна строка команды
для оболочки, поэтому пробелы внутри одного значения не создают новые аргументы.

Поэтому такой пример безопасно сохраняет пробелы внутри значения:

```yesh
path = "backup files/source"
printf '%s\n' $path
```

Пустая строка — один аргумент, пустой список — ни одного аргумента. Ошибка
раскрытия обнаруживается до запуска внешней команды.

## 9. Переменные окружения

Чтобы получить обязательное значение от вызывающего процесса, используйте
форму `environment`:

```yesh
source = environment YESH_BACKUP_SOURCE
target = environment YESH_BACKUP_TARGET

if exists $source:
    printf '%s\n' $source $target
else:
    echo "backup source is missing"
    exit 2
```

Если этот фрагмент сохранён как `environment-check.yesh`, значения можно задать
при запуске:

```text
YESH_BACKUP_SOURCE=source YESH_BACKUP_TARGET=backup ./yesh environment-check.yesh
```

Имя переменной окружения пишется без `$`: это часть объявления. Если значение
отсутствует или пусто, yesh сообщает об ошибке в момент этого присваивания.
Это не означает, что проверка всех обязательных значений произошла до первой
команды: если перед присваиванием уже были действия с побочными эффектами,
они могли выполниться. Для гарантии «до любых изменений» соберите все
обязательные значения в начале сценария или вынесите отдельный предварительный
сценарий без изменяющих команд.

## 10. Регулярное выражение и `matches`

Регулярное выражение — отдельное значение, а `matches` — отдельное условие:

```yesh
unit = "api-42"
pattern = regex '^api-[0-9]+$'

if $unit matches $pattern:
    echo "service name is valid"
else:
    echo "service name is invalid"
    exit 3
```

Шаблон использует синтаксис Go RE2. Он проверяется при присваивании. Текст
`"a matches b"` остаётся строкой и не превращается в оператор.

Регулярное выражение здесь только сопоставляет или извлекает текст. Оно не
определяет структуру yesh и не заменяет обычные операции со строками, списками,
файлами или процессами. Если задачу можно выразить явным сравнением или
внешней Linux-командой с понятными аргументами, новый regex для неё не нужен.

## 11. План и сообщения об ошибках

`--plan` полезен для проверки порядка действий и раскрытых аргументов:

```text
./yesh --plan check-source.yesh
```

План не запускает внешние команды и не открывает перенаправления. Для внешней
стадии он показывает точный список аргументов команды (`argv`), который yesh
передал бы программе. Встроенная операция yesh, например `publish`, показывается
как планируемое действие со своими параметрами, а не как `argv` внешней команды.
План показывает структуру возможного выполнения: для условных действий он
показывает обе ветви. Это не предсказание того, какая ветвь будет выбрана при
настоящем запуске. План не может заранее гарантировать, что сеть, файловая
система, служба или внешняя программа останутся доступными к этому моменту.

Смысл здесь не в том, чтобы сократить трёхстрочный сценарий: маленький пример
на Bash может быть таким же коротким. Преимущество проявляется, когда сценарий
растёт: yesh оставляет видимыми границы аргументов, публикацию, поведение при
ошибке и порядок действий, чтобы их можно было проверить при чтении.

Если команда уже запущена и завершается ошибкой, yesh сообщает имя файла,
номер строки и причину остановки. Ошибку выполнения нельзя превратить в
обычное ложное условие, добавив `else`.

Например, это не обработка отсутствующей команды:

```yesh
if missing-command:
    echo "not reached"
else:
    echo "also not reached"
```

Если команда не найдена, сценарий завершается ошибкой выполнения. В `else`
переходит только обычная команда, которая запустилась и вернула ненулевой
код.

### Граница ответственности

Полезно разделять то, что проверяет yesh, и то, что знает внешняя система:

| yesh | Внешняя система или команда |
| --- | --- |
| порядок действий и ветвление | состояние сети, службы и файловой системы |
| точные аргументы внешнего вызова | смысл и результат работы утилиты |
| остановка после ошибки и отсутствие следующего действия | изменения, которые уже произошли до ошибки |
| план запуска без выполнения команд | то, что может измениться между планом и запуском |

Поэтому `--plan` помогает проверить намерение сценария, но не обещает, что
внешняя команда позже завершится успешно.

## 12. Административные границы

Для повторяющихся административных действий есть отдельные операции с ясно
описанными ограничениями:

```yesh
with lock /var/lib/yesh/backup.lock:
    rsync -a -- source/ temporary/
    publish temporary to current
```

`with lock` задаёт блокировку (`lock`): yesh не ждёт её освобождения и освобождает
её при любом выходе.
Сначала yesh готовит новый файл или каталог во временном месте. После успешной
проверки `publish` за одну операцию заменяет старый результат новым. Если
блокировка уже занята, тело сценария не начинается. Если `rsync` завершается
ошибкой, `publish` не выполняется. Если
источник и назначение находятся в разных файловых системах, операция
отклоняется вместо незаметного копирования. Технически для этого используется
переименование в одной файловой системе. `publish` не объединяет каталоги:
в этом фрагменте `current` должен быть отсутствующим именем или заменяемой
символьной ссылкой на прежний результат.

yesh не повышает права сам, не заменяет `rsync`, `systemctl`, `tar` или другие
Linux-команды и не является оболочкой. Команда, сеть, файловая система и
состояние службы могут изменить результат после проверки.

## 13. Полный сценарий замены подготовленного файла

### Какую проблему решает yesh

Без такой последовательности проверка может быть выполнена после замены файла
или ошибка проверки может оставить новый файл видимым. yesh удерживает порядок
«подготовленный файл → проверка содержимого → публикация» и оставляет прежний
файл неизменным при отказе внешней команды.

Подготовим проверенный файл и заменим им действующий только после успешной
проверки:

```yesh
staged = "active.conf.next"
active = "active.conf"

if exists $staged:
    grep -q '^mode=production$' $staged
    publish $staged to $active
    echo "configuration published"
else:
    echo "prepared configuration is missing"
    exit 2
```

Здесь yesh задаёт порядок: сначала проверяется наличие подготовленного файла,
затем внешняя команда проверяет его содержимое, затем `publish` заменяет
действующий файл подготовленным. Если проверка не пройдена, старый файл
остаётся нетронутым.
Если `grep` завершается ошибкой, замена не выполняется. Если подготовленный
файл отсутствует, сценарий завершается до запуска внешней команды.

Это не проверка того, что приложение полностью готово работать с новой
конфигурацией. Для этого нужны отдельная проверка приложения и, при
необходимости, операция службы с требуемым состоянием после перезапуска.

## 13а. Безопасное развёртывание статического релиза

Этот сценарий показывает, как собрать из уже существующих конструкций yesh
публикацию небольшого статического сайта. Он не добавляет в язык отдельные
команды `deploy`, `http`, `sudo` или `rollback`: проверка службы, публикация,
переключение ссылки и HTTP-запрос остаются видимыми внешними действиями.

Полный вариант находится в [`deploy-static.yesh`](../examples/deploy-static.yesh)
для nginx под OpenRC. Для Alpine с lighttpd есть
[`deploy-static-openrc-lighttpd.yesh`](../examples/deploy-static-openrc-lighttpd.yesh),
а для nginx под systemd —
[`deploy-static-systemd.yesh`](../examples/deploy-static-systemd.yesh).
Синтаксис у них один и тот же; меняются только команда проверки службы и
проверка конфигурации веб-сервера.

Подготовленный каталог не следует сразу делать значением `current`: сначала
нужно дать ему окончательное имя релиза, а затем отдельно заменить ссылку
`current`. Поэтому пути передаются полностью через окружение:

```yesh
release = environment YESH_RELEASE
release_index = environment YESH_RELEASE_INDEX
release_final = environment YESH_RELEASE_FINAL
current = environment YESH_CURRENT
current_next = environment YESH_CURRENT_NEXT
previous = environment YESH_PREVIOUS
lock = environment YESH_DEPLOY_LOCK
health_url = environment YESH_HEALTH_URL
```

В yesh нет неявного присоединения текста к переменной: `$release/index.html`
не является ссылкой на файл внутри `$release`. Поэтому полный путь к
`index.html` задаётся отдельной переменной `YESH_RELEASE_INDEX`. Это сохраняет
границы аргументов и не вводит новую модель подстановки путей.

Основной порядок действий выглядит так:

```yesh
if exists $release:
    with lock $lock:
        if exists $release_index:
            /usr/sbin/nginx -t
            publish $release to $release_final
            ln -s -- $release_final $current_next
            mv -T -- $current_next $current

            if curl --fail --silent --show-error --max-time 10 $health_url:
                echo "HTTP check passed"
            else:
                ln -s -- $previous $current_next
                mv -T -- $current_next $current
                exit 4
```

Полный пример дополнительно проверяет, что `current` и предыдущий релиз имеют
ожидаемый вид, а имена нового релиза и временной ссылки ещё не заняты. Это
защищает от случайного перезаписывания и делает повторный запуск явным
отказом, если его состояние не соответствует ожиданиям. `publish` использует
переименование в одной файловой системе и не заменяет существующее имя;
`ln` и `mv -T` поэтому оставлены отдельными видимыми командами для смены
`current`.

Если HTTP-проверка не проходит, предыдущая ссылка возвращается, а сценарий
завершается с кодом `4`. Это компенсация уже выполненной публикации, а не
транзакция файловой системы: если процесс будет прерван между сменой ссылки и
откатом, автоматической гарантии возврата нет. Старый и новый каталоги также
не удаляются этим примером.

Проверка конфигурации веб-сервера и права запуска — отдельная граница. yesh не
вызывает `sudo` и не получает права сам. В боевом безнадзорном запуске весь
сценарий обычно выполняют от `root` либо используют отдельную внешнюю политику
для специальной учётной записи. Интерактивный запрос пароля `sudo` не является
надёжным способом запуска из задания. В частности, `nginx -t` открывает не
только файл PID, но и файлы, перечисленные конфигурацией; одних прав на
`/run/nginx.pid` недостаточно.

Эквивалентная идея на Bash требует вручную сохранить те же границы:

```bash
flock -n "$YESH_DEPLOY_LOCK" bash -c '
  test -f "$YESH_RELEASE_INDEX" || exit 3
  nginx -t || exit 1
  mv -- "$YESH_RELEASE" "$YESH_RELEASE_FINAL" || exit 1
  ln -s -- "$YESH_RELEASE_FINAL" "$YESH_CURRENT.next" || exit 1
  mv -T -- "$YESH_CURRENT.next" "$YESH_CURRENT" || exit 1
  curl --fail --silent --show-error --max-time 10 "$YESH_HEALTH_URL" || {
    ln -s -- "$YESH_PREVIOUS" "$YESH_CURRENT.next"
    mv -T -- "$YESH_CURRENT.next" "$YESH_CURRENT"
    exit 4
  }
'
```

Правило примера: сначала проверяется подготовленный релиз и конфигурация,
потом под блокировкой публикуется новый каталог, после переключения проверяется
HTTP-ответ, а при его отказе возвращается прежняя ссылка. Перед обычным запуском
проверьте `--plan`; затем на отдельном стенде проверьте успех, отказ HTTP,
неверную конфигурацию, занятую блокировку и оставшееся старое состояние.

### Что именно доказано на стенде

Практический результат этого примера — не обещание «безопасного деплоя вообще»,
а проверенный порядок действий на одном узле. На Alpine с OpenRC и lighttpd, а
также на Debian с systemd и nginx стенд подтверждает следующее:

- второй запуск не входит в тело сценария, если lock уже занят;
- неверная конфигурация веб-сервера останавливает работу до публикации;
- новый каталог становится доступен через `current` только после успешной
  проверки подготовки;
- ответ `2xx` делает публикацию успешной;
- ошибка HTTP возвращает ссылку на предыдущий релиз и даёт код `4`;
- старое имя `current.next` останавливает сценарий до изменения состояния.

Для systemd-проверки из репозитория есть
[стендовый скрипт](../scripts/yesh-deploy-static-systemd-fixture.sh). Он
создаёт временный каталог внутри корня сайта, поэтому перед запуском нужно
знать действующий `root` nginx и иметь права для `nginx -t`:

```text
sudo YESH_BIN=/path/to/yesh \
  YESH_SCRIPT=/path/to/yesh/examples/deploy-static-systemd.yesh \
  YESH_WEB_ROOT=/var/www/html \
  /path/to/yesh/scripts/yesh-deploy-static-systemd-fixture.sh
```

Скрипт сначала показывает план, затем публикует рабочий релиз, моделирует
ошибку HTTP и проверяет откат. В конце он отдельно прерывает запуск после
переключения `current`. Ожидаемый результат последней проверки — новый релиз
остаётся активным. Это не ошибка теста: yesh не может вернуть имя назад после
внезапного завершения, если отдельный процесс не успел выполнить
компенсационный шаг.

Поэтому правильная формулировка гарантии такова: yesh делает порядок проверки,
публикации и обычного отката видимым и проверяемым; он не превращает несколько
операций файловой системы в транзакцию и не доказывает поведение DNS, кешей,
TLS, клиентов или содержимое приложения за пределами выбранного URL.

## 13б. Практический пример: rsnapshot

### Какую проблему решает yesh

Администратор может перепутать проверку конфигурации, пробный режим и ротацию либо
запустить изменение без просмотра фактических команд. yesh разделяет эти шаги,
требует явного подтверждения и проверяет ожидаемый результат; саму передачу и
ротацию по-прежнему выполняет `rsnapshot`.

Теперь соберём те же правила вокруг внешней утилиты `rsnapshot`. yesh не
разбирает и не переписывает `rsnapshot.conf` и не выполняет ротацию сам. Его
роль — проверить предпосылки, показать пробный запуск, потребовать явного
подтверждения и проверить результат. Он упрощает чтение административного
сценария: порядок проверок виден сверху вниз, граница между пробным режимом и
изменением выражена отдельной ветвью, аргументы `rsnapshot` остаются явными,
а ошибка останавливает следующий шаг без набора Bash-флагов и скрытых условий.

Перед чтением сценария полезно вспомнить модель `rsnapshot`:

### Две разные модели: `rsync` и `rsnapshot`

`rsync` — это прежде всего передача и согласование одного источника с одним
назначением. Он сравнивает деревья и приводит назначение к выбранной политике
копирования; при явно переданном `--delete` лишние данные назначения могут быть
удалены. `--dry-run` показывает пробный результат и не меняет файлы, но это
только прогноз одной передачи.

`rsnapshot` — это не другой протокол передачи, а организатор последовательности
снимков поверх `rsync`. Он хранит несколько именных состояний (`daily.0`,
`daily.1` и т. п.), сначала сдвигает и удаляет старые уровни по правилам
`retain`, а затем выполняет передачу для нужного интервала. Неизменённые файлы
между уровнями обычно представлены жёсткими ссылками, поэтому каждый уровень
выглядит как полное дерево, хотя место занимают в основном изменения.

👀 Конкретная конфигурация `rsnapshot` может передавать в пробный вывод
`--delete` и `--delete-excluded`. Это флаги передаваемого `rsync`: они не удаляют
источник, но приводят новое дерево снимка к содержимому источника и могут удалить
лишнее в назначении. Поэтому нужно смотреть реальный `rsnapshot -t`, а не только
исходный файл yesh; сценарий отмечает такие флаги и останавливается до явного
подтверждения.

Отсюда разные вопросы администратора:

- для `rsync`: «какое дерево должно получиться в этом назначении и что будет
  передано или удалено?»;
- для `rsnapshot`: «какие моменты времени должны сохраниться, какой интервал
  сейчас передаёт данные, какой старый уровень будет вытеснен и можно ли
  безопасно выполнить ротацию?»

👀 Практическая проверка обычного `rsync -a` проста: после изменения источника
изменённый файл появляется в выводе, а повторный запуск без новых изменений
обычно не выводит передачи. Файл, который есть только в назначении, остаётся
на месте: удаление начинается только с явно переданного флага вроде
`--delete`. Поэтому перед запуском нужно отдельно посмотреть план и список
аргументов, а не предполагать политику по одному слову «резервная копия».

💡 yesh упрощает не выбор между этими инструментами, а чтение границы вокруг
  них: для `rsync` — проверка, временное дерево и публикация одного результата;
  для `rsnapshot` — `configtest`, пробный режим, просмотр ротации и явное
  подтверждение. Передача и ротация остаются ответственностью внешней утилиты.

- `snapshot_root` — корень, в котором утилита хранит уровни снимков;
- `retain daily 2` оставляет `daily.0` как самый новый уровень и `daily.1` как
  предыдущий;
- неизменённые файлы между уровнями обычно используют общие жёсткие ссылки;
  снимок нельзя считать независимой копией для редактирования на месте;
- `no_create_root 1` запрещает молча создавать корень. В нашем примере корень
  должен уже существовать и быть именно ожидаемой точкой монтирования;
- запись вида `backup /path/./ local/` задаёт границу исходного дерева: часть
  пути до `/./` не попадает в каталог снимка;
- `rsnapshot -t` показывает действия выбранного уровня, но не заменяет
  `configtest` и не доказывает, что передача завершится успешно.

`configtest` — встроенная проверка самого `rsnapshot`: она проверяет синтаксис
конфигурации и необходимые программы, но не выполняет резервное копирование и
не меняет снимки. Режим `-t LEVEL` идёт следующим шагом: он показывает
предполагаемые команды выбранного уровня без ротации, но тоже не доказывает,
что будущая передача завершится успешно.

Минимальные параметры такой временной конфигурации выглядят примерно так;
между полями конфигурации используется табуляция:

```text
config_version	1.2
snapshot_root	/backup/snapshots/
no_create_root	1
retain	daily	2
lockfile	/tmp/rsnapshot.pid
backup	/srv/data/./	local/
```

👀 В рабочей системе пути, `lockfile`, команды и параметры `rsync` должны быть
проверены по конкретному `rsnapshot.conf`. yesh не угадывает их и не заменяет
проверку конфигурации.

Полный файл находится в
[`examples/rsnapshot-apply.yesh`](../examples/rsnapshot-apply.yesh). Его входы
передаются через окружение:

```yesh
config = environment YESH_RSNAPSHOT_CONFIG
level = environment YESH_RSNAPSHOT_LEVEL
sync_first = environment YESH_RSNAPSHOT_SYNC_FIRST
root = environment YESH_RSNAPSHOT_ROOT
mount_source = environment YESH_RSNAPSHOT_SOURCE
lock = environment YESH_RSNAPSHOT_LOCK
report = environment YESH_RSNAPSHOT_REPORT
published = environment YESH_RSNAPSHOT_PUBLISHED
confirm = environment YESH_RSNAPSHOT_CONFIRM
```

Сокращённая последовательность сценария выглядит так; полный файл также
сообщает о незмонтированном назначении и нехватке места:

```yesh
if exists $config:
    if findmnt --source $mount_source --target $root:
        if free_space $root at_least 20MiB:
            rsnapshot -c $config configtest
            if $sync_first matches regex "1":
                rsnapshot -c $config -t sync | tee $report
                rsnapshot -c $config -t $level | tee -a $report
            else:
                rsnapshot -c $config -t $level | tee $report
            if exists $confirm:
                if $sync_first matches regex "1":
                    rsnapshot -c $config sync
                rsnapshot -c $config $level
                if exists $published:
                    if exists $lock:
                        echo "rsnapshot lockfile remains after successful interval"
                        exit 6
                    else:
                        echo "rsnapshot interval completed"
```

Сначала проверяется файл конфигурации, точное монтирование и свободное место.
Затем `configtest` проверяет конфигурацию, а `-t` показывает
действия выбранного уровня без ротации и одновременно сохраняет этот план в
отчёт через `tee`. yesh отмечает в отчёте известные флаги удаления, но не
объявляет конфигурацию безопасной автоматически. Только наличие заранее
созданного файла подтверждения разрешает изменяющую команду. После неё проверяется
ожидаемый путь из `$published` и отсутствие файла блокировки.

Вызов `rsnapshot` остаётся видимым: по нему можно заранее понять, какой файл
конфигурации и какой уровень будут переданы. В режиме `--plan` yesh показывает
обе ветви, но не запускает `findmnt`, `rsnapshot` и не открывает файлы.

Эквивалентная Bash-идея потребовала бы вручную удерживать порядок проверок:

```bash
rsnapshot -c "$config" configtest || exit 1
if [ "$sync_first" = 1 ]; then
    rsnapshot -c "$config" -t sync || exit 1
    rsnapshot -c "$config" -t "$level" || exit 1
else
    rsnapshot -c "$config" -t "$level" || exit 1
fi
test -e "$confirm" || exit 4
if [ "$sync_first" = 1 ]; then
    rsnapshot -c "$config" sync || exit 1
fi
rsnapshot -c "$config" "$level" || exit 1
test -d "$published" || exit 6
test ! -e "$lock" || exit 6
```

Правило примера: пробный режим и явное подтверждение идут до изменяющего
запуска, а отсутствие ожидаемого снимка или оставшийся файл блокировки превращают запуск
в ошибку. yesh не откатывает уже выполненную ротацию и не удаляет карантин.

Для полного Р.П.П. используется
[`yesh-rsnapshot-loopback-rwe.sh`](../scripts/yesh-rsnapshot-loopback-rwe.sh):
он создаёт одноразовый ext4-образ с loop-устройством и проверяет две ротации,
восстановление, жёсткие ссылки, неверную конфигурацию, отсутствие
подтверждения, занятый файл блокировки и освобождение ресурсов. Реальные диски и
`/etc/rsnapshot.conf` в нём не используются.

## SSH-ключи для источника на другом узле

### Какую проблему решает yesh

Без явной настройки SSH сценарий может зависнуть на запросе пароля или принять
непроверенный ключ узла. yesh оставляет параметры подключения видимыми и
останавливает вызов без скрытого запроса; ключи, доверие к узлу и права остаются
ответственностью OpenSSH.

`rsync`, `rsnapshot`, `ssh` и `scp` для другого узла не получают пароль из сценария
yesh. OpenSSH берёт ключ из обычной конфигурации, агента или явно указанного
файла. Закрытый ключ остаётся на машине, где запускается yesh; на другом узле
помещается только открытый ключ.

Для отдельного тестового пользователя настройка выглядит так:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/yesh_test_ed25519
ssh-copy-id -i ~/.ssh/yesh_test_ed25519.pub backup@example.test
```

👀 Перед автоматическим запуском один раз проверьте отпечаток ключа узла через
доверенный канал и сохраните его в `~/.ssh/known_hosts`. `ssh-keyscan` может
получить ключ, но сам по себе не доказывает, что узел настоящий: его вывод
нужно сравнить с отпечатком, полученным от владельца узла или из другого
доверенного источника.

Проверка без запроса пароля:

```bash
ssh -o BatchMode=yes \
    -o ConnectTimeout=5 \
    -o StrictHostKeyChecking=yes \
    backup@example.test true
```

В сценарии yesh эти параметры остаются видимыми:

```yesh
host = environment YESH_SSH_HOST
ssh_options = [-o, BatchMode=yes, -o, ConnectTimeout=5, -o, StrictHostKeyChecking=yes]

if ssh $ssh_options $host test -d /srv/data:
    echo "remote source is ready"
else:
    echo "remote source is unavailable"
    exit 2
```

Для `rsync` те же параметры передаются через `-e` или через обычную запись в
`~/.ssh/config`. Не включайте `StrictHostKeyChecking=no`, не храните закрытый
ключ, пароль или его содержимое в `.yesh`-файле и не используйте `sshpass`.
`BatchMode=yes` нужен для того, чтобы отсутствие ключа было явной ошибкой, а не
зависшим запросом пароля.

Правило: yesh проверяет порядок и границы вызова на другом узле, а OpenSSH отвечает
за ключ, доверие к узлу и права пользователя.

Типичные ошибки здесь не являются ошибками yesh: неверный пользователь,
неустановленный открытый ключ, отсутствующий `known_hosts`, неправильный
отпечаток, запрещённая команда или отсутствие `rsync` на другом узле.
👀 Сначала проверьте тот же вызов `ssh` отдельно, затем запускайте сценарий с
`--plan` и только после этого выполняйте изменяющий шаг.

## 13в. Измерение службы systemd за заданный период

Новое в `0.2.0`: снимки ресурсов службы только для чтения и конечные измерения
с ограниченной историей JSONL. В этой главе описан текущий вариант для
Linux/systemd.

На узле Linux с единой иерархией cgroup v2 systemd управляет иерархией,
смонтированной в `/sys/fs/cgroup`. Для каждого юнита службы systemd создаёт или
назначает отдельную cgroup; например, `your-service.service` обычно находится
по пути `/sys/fs/cgroup/system.slice/your-service.service/`. Эта cgroup служит
корнем дерева службы, которое наблюдает yesh. У службы могут быть дочерние
cgroup, но для самостоятельного управления ими ей нужен `Delegate=yes`.

### Какую проблему решает yesh

Без связанного снимка администратор вручную сопоставляет службу, cgroup, PID и
счётчики и может смешать два запуска. yesh собирает их в конечное измерение,
сохраняет историю и останавливает сравнение при смене идентичности службы.

Здесь нужен ответ не только на вопрос «что со службой сейчас?», но и на вопрос,
что с ней происходило последний час или сутки.

Идея простая:

```text
measure → сохранить снимки → summarize → увидеть изменение
```

Например, можно увидеть, росла ли память, сколько процессорного времени и
дискового ввода-вывода использовала служба, были ли события OOM (Out Of Memory
— нехватка памяти), и не началось ли странное поведение после перезапуска.
Один снимок отвечает только
на вопрос «что происходит сейчас».
`measure` берёт несколько снимков за конечный промежуток и сохраняет их как
один результат.

Вот полный пример:

```yesh
# В каталоге будут measurements.jsonl и файл блокировки. summarize читает
# оттуда историю; /tmp нужен только для этого короткого упражнения.
state_dir = "/tmp/yesh-nginx-resources"

measure service nginx.service for 30s every 5s:
    save to $state_dir
    keep history for 24h
summarize service nginx.service from $state_dir since 1h
```

В строке `measure` указано всё, что нужно для самого измерения:

- `service` указывает, что измеряем службу, которой управляет systemd;
- `nginx.service` — точное имя службы;
- `for 30s` ограничивает всё измерение тридцатью секундами;
- `every 5s` задаёт интервал между снимками.

Отдельного ключевого слова `unit` нет: имя службы просто идёт после `service`
и, при необходимости, после `user` или `system`. `save to` задаёт путь
истории. В примере обе команды используют один и тот же `$state_dir`: первая
записывает туда, вторая читает оттуда. Путь, оканчивающийся на `.jsonl`, задаёт
сам файл журнала; любой другой путь задаёт каталог, внутри которого будет
`measurements.jsonl`. После успешной записи директива
`keep history for 24h` удаляет из этого журнала результаты старше суток.

История хранится в `measurements.jsonl`. Это не один большой JSON-документ и
не журнал команд: каждый завершённый запуск `measure` записывается одной
самостоятельной строкой, а снимки этого запуска находятся внутри записи.
Запись появляется только после завершения сбора. Если процесс оборвался в
середине последней строки, старые записи остаются читаемыми; если полностью
записанная строка повреждена, yesh останавливается с ошибкой, а не молча
пропускает её. Поэтому JSONL подходит для ограниченной локальной истории, но
не является базой данных или механизмом возобновления работы.

Если `save to` не указан, путь журнала по умолчанию имеет вид
`~/.local/yesh/<unit>.jsonl`; для nginx это
`~/.local/yesh/nginx.service.jsonl`. yesh создаёт только недостающий родительский
каталог внутри домашнего каталога пользователя с правами `0700` и не требует и не вызывает
`sudo`; привилегированного родителя он не создаёт и не исправляет. Доступ к
системной службе или её журналу всё равно определяется правами машины. Явно
указанный каталог состояния должен быть доступен для записи текущему пользователю;
его существующие права yesh не меняет.

Двоеточие после первой строки означает, что ниже идут настройки именно этого
измерения. Поэтому это расширенная форма. Если не нужно отдельно указывать
каталог и срок хранения, используйте короткую форму:

```yesh
measure service nginx.service for 30s every 5s
```

Короткая форма всё равно сохраняет результат в каталог по умолчанию, но не
задаёт очистку истории. Для длительного использования укажите срок хранения.

Измерение имеет конечную длительность: первый снимок делается сразу,
последующие — через заданный интервал, а запись появляется только после
завершения сбора. `summarize` только читает историю: службу он не запускает и
новые снимки не делает. Перед запуском полезно посмотреть план:

```text
yesh --plan service-measurement.yesh
```

💡 Вот что упрощает yesh: служба, период наблюдения, сохранённая история, изменения
ресурсов и нужное окно журнала остаются в одной понятной проверке. Linux-команды
не скрываются, но теперь не нужно восстанавливать их область, порядок и
ограничения по множеству отдельных команд оболочки.

Не путайте неполный отдельный снимок с неполным измерением. Снимок может быть
частичным, если недоступно необязательное поле, например ввод-вывод блока; всё
измерение всё равно может получить `complete=true`, если его срок завершён и
идентичность службы не менялась. Исчезнувшая cgroup или процесс во время сбора
делают сохранённый интервал неполным.

Старую историю можно читать при следующем запуске. `summarize ... since 1h`
берёт из журнала записи за последний час, сравнивает начало и конец каждого
измерения, собирает их в общий отчёт и показывает изменения памяти, RSS, CPU,
OOM и операций ввода-вывода. Человекочитаемый отчёт отмечает направление памяти
и RSS знаками `↑`, `↓`, `=` или `~`; навигатор также показывает изменение между
соседними сохранёнными записями. Он не продолжает оборванное измерение и не
смешивает записи разных запусков службы. Для продолжения нужен новый явный
`measure`.

RSS — это резидентная память процесса: объём его памяти, который сейчас
находится в оперативной памяти. Общие страницы могут учитываться у нескольких
процессов, а страницы, вытесненные в swap, в RSS не входят. Само значение RSS,
полученное от ядра, является оценкой. Поэтому RSS — это показатель отдельного
процесса, а не точная уникальная стоимость памяти службы.

У результата есть важные границы:

- это наблюдение cgroup выбранной службы и, если они есть, вложенных cgroup в
  конкретный момент, а не доказательство причины роста или неисправности;
- `memory.current` показывает значение памяти для наблюдаемой области cgroup, а
  RSS — память отдельных процессов; сумму RSS нельзя выдавать за
  `memory.current`;
- память и RSS — текущие значения, а CPU и ввод-вывод — счётчики, для которых
  нужны дельты между снимками;
- недоступный счётчик обозначается как `unavailable` («недоступен»), а не как ноль;
- история хранится ограниченным журналом JSON Lines: незавершённая последняя
  строка не считается готовым результатом, а повреждённая завершённая запись —
  ошибкой.

Каждая запись относится к конкретному диспетчеру systemd, имени службы, пути cgroup и
идентификатору её запуска (`InvocationID`, если он доступен). После перезапуска
службы нельзя молча смешивать два запуска в одну историю. Эти ограничения нужны,
чтобы отчёт показывал измеренное изменение, а не придуманное объяснение.

В Bash для той же задачи обычно пришлось бы отдельно продумать цикл, таймер,
временный файл и очистку:

```bash
for i in 1 2 3 4 5; do
    systemctl show nginx.service
    sleep 2
done
```

Этот цикл лишь несколько раз печатает состояние. Историю, сравнение и очистку
к нему пришлось бы добавлять отдельно.

Сам по себе этот цикл не задаёт, где хранить результат, сколько его хранить и
как не смешать разные запуски службы. В yesh эти границы видны прямо в
сценарии. Нужны Linux, доступный systemd и читаемая cgroup v2.

Для обычной службы настройки systemd-юнита менять не нужно: systemd уже помещает
её процессы в собственную cgroup. `Delegate=yes` требуется только службе,
которая сама создаёт вложенные cgroup и размещает в них свои процессы.
Параметры `CPUAccounting=`, `MemoryAccounting=` и `IOAccounting=` могут открыть
отдельные счётчики, но их наличие зависит также от ядра, systemd и действующей
политики. Поэтому недоступный счётчик yesh показывает как `unavailable`, а не
как ноль.

## 13г. Ротация текстовых журналов службы

### Какую проблему решает yesh

Один сценарий легко начинает одновременно вмешиваться в journald и `logrotate`,
дублировать удаление или перезапускать службу без проверки результата. yesh
делит владельцев журналов, связывает пробный и изменяющий запуск и проверяет
состояние службы после операции; ротацию и сжатие выполняет `logrotate`.

Рассмотрим близкий к рабочему сценарий: у `nginx` есть два независимых потока
сообщений. Вывод службы читает `systemd-journald`, а файлы
`/var/log/nginx/*.log` обслуживает `logrotate`. Это не один общий журнал, и
одна команда не должна незаметно обслуживать оба источника.

yesh здесь не удаляет старые файлы и не пытается определить владельца пути.
Его роль проще: связать в читаемом порядке проверку службы, свободного места,
пробный запуск настоящей политики `logrotate`, явное подтверждение изменения
и проверку после операции. Политика, файл состояния, сжатие, удаление и
`postrotate` остаются ответственностью `logrotate`.

Полный сценарий —
[`examples/nginx-logrotate-maintenance.yesh`](../examples/nginx-logrotate-maintenance.yesh).
Его важная часть выглядит так:

```yesh
config = environment YESH_NGINX_LOGROTATE_CONFIG
state = environment YESH_NGINX_LOGROTATE_STATE
lock = environment YESH_NGINX_LOGROTATE_LOCK
confirm = environment YESH_NGINX_LOGROTATE_CONFIRM
binary = environment YESH_NGINX_LOGROTATE_BIN

with lock $lock:
    service status nginx.service
    df -P -h -- /var/log
    $binary -d -v -s $state $config

    if exists $confirm:
        $binary -s $state $config
    else:
        echo "nginx logrotate plan reviewed; confirmation file is missing"
        exit 5

    df -P -h -- /var/log
    service status nginx.service
    journal nginx.service since 5m lines 40
```

`-d -v` — пробный запуск самого `logrotate`: он читает ту же политику и файл
состояния, но не выполняет ротацию. Только заранее созданный файл подтверждения
разрешает следующий вызов без `-d`. Проверяется лишь наличие этого файла; его
содержимое не является паролем и не читается. Если подтверждения нет, сценарий
завершается до изменения журналов.

Запуск на реальной машине требует передать пути из действующей политики, а не
придумать их по имени каталога:

```text
export YESH_NGINX_LOGROTATE_CONFIG=/etc/logrotate.d/nginx
export YESH_NGINX_LOGROTATE_STATE=/var/lib/logrotate/status
export YESH_NGINX_LOGROTATE_LOCK=/run/lock/yesh/nginx-logrotate.lock
export YESH_NGINX_LOGROTATE_CONFIRM=/run/yesh/confirm-nginx-logrotate
export YESH_NGINX_LOGROTATE_BIN=/usr/sbin/logrotate
yesh --plan examples/nginx-logrotate-maintenance.yesh
```

Если план проверен и окно обслуживания выбрано, подтверждение создаётся
отдельной командой, а затем сценарий запускается ещё раз:

```text
install -m 0600 /dev/null "$YESH_NGINX_LOGROTATE_CONFIRM"
yesh examples/nginx-logrotate-maintenance.yesh
```

Создание файла подтверждения — действие администратора, а не скрытая часть yesh.
Если политика не должна применяться, этот файл создавать не нужно.

Порядок такой: служба и место на диске, пробная политика, отказ без
подтверждения или настоящая операция, затем повторные проверки и ограниченный
просмотр журнала. Запрос `journal` в конце только читает недавние записи через
`journalctl`; он не вращает и не очищает хранилище journald. Для очистки
journald нужна отдельная операция через `journalctl --rotate` и `--vacuum-*` с
собственным планом и подтверждением.

Эквивалентная Bash-идея требует вручную удерживать те же границы:

```bash
systemctl is-active --quiet nginx.service || exit 1
df -P -h -- /var/log || exit 1
logrotate -d -v -s "$state" "$config" || exit 1
test -e "$confirm" || exit 5
logrotate -s "$state" "$config" || exit 1
df -P -h -- /var/log || exit 1
systemctl is-active --quiet nginx.service || exit 1
journalctl --no-pager --unit nginx.service --since -5m --lines 40
```

Правило примера: yesh организует видимый порядок и границу подтверждения, но
не подменяет `logrotate`, `systemctl` или `journalctl`, не угадывает владельца
файла и не обещает откат уже выполненной ротации. Сценарий применим только
тогда, когда `$config` — действительно действующая политика для этих файлов.
Подробности испытания Debian и отрицательные случаи находятся в
[результатах Linux-проверок](underthehood/linux-integration.ru.md).

## 14. Как читать незнакомый сценарий

При разборе yesh-сценария задайте пять вопросов:

1. Какие значения задаются и где раскрываются через `$`?
2. Какие внешние команды запускаются и какие аргументы они получают?
3. Какие файлы, службы или другие объекты могут измениться?
4. Что произойдёт при ненулевом коде, отсутствии цели или отказе доступа?
5. Что покажет `--plan`, и какие внешние условия всё равно могут измениться?

Если на какой-то вопрос нельзя ответить по самому тексту и правилам языка,
сценарий надо уточнить до запуска.

## 15. Проверка перед запуском

Слово «проверка» здесь означает несколько разных механизмов. Их полезно не
смешивать:

| Проверка | Что вы узнаёте |
| --- | --- |
| Разбор сценария | Корректность синтаксиса и поддерживаемых конструкций |
| `--plan` | Предполагаемые действия и аргументы без их исполнения; обе ветви условия показываются как возможные |
| Проверка перед действием | Состояние системы в этот момент, например наличие пути или нужная файловая система |
| Результат после действия | Наблюдаемый результат, например состояние службы или опубликованный файл |
| Проверка на временном стенде | Поведение конкретного сценария в одном испытанном окружении |

Ни один из этих механизмов не заменяет остальные: успешный разбор не проверяет
хост, план не выполняет команды, а стендовый тест не обещает такое же поведение
на другой системе.

Перед обычным запуском убедитесь, что:

- обязательные переменные окружения заданы и не пусты;
- каждое значение раскрывается явно через `$name`;
- внешний вызов получает именно те аргументы, которые вы ожидаете;
- изменяющие команды работают с временными путями до публикации;
- отказ внешней команды не приводит к ложному сообщению об успехе;
- `--plan` показывает структуру возможного порядка действий и обе ветви
  условий; он не утверждает, какая ветвь будет выбрана при запуске.

Если сценарий требует `sudo`, задайте его снаружи и проверьте план и обычный
запуск в одном и том же окружении. yesh не добавляет повышение прав сам.

## 16. Упражнение

Напишите сценарий `publish-report.yesh`, который берёт из окружения
`YESH_REPORT_SOURCE`, `YESH_REPORT_TEMP` и `YESH_REPORT_CURRENT`, а затем:

1. проверяет наличие исходного файла;
2. создаёт отчёт во временном пути с помощью внешней команды;
3. не публикует отчёт после ошибки этой команды;
4. публикует временный результат только после успеха;
5. возвращает код `2`, если исходный файл отсутствует;
6. показывает план без запуска внешней команды и изменения файлов.

Проверьте три случая: обычный успех, отсутствующий источник и команда,
завершающаяся с ошибкой. В последнем случае заранее определите, что должно
остаться от временного результата, и убедитесь, что прежний опубликованный
файл не заменён и ложного сообщения об успехе нет.

Решение должно использовать только существующие конструкции yesh. Если для
него требуется новая встроенная операция, сначала проверьте, нельзя ли
выразить задачу последовательностью обычных Linux-команд.

## 17. Если что-то пошло не так

- **`yesh: command not found`** — соберите бинарный файл или укажите его
  полный путь. Для первого запуска из репозитория используйте `./yesh`.
- **`environment NAME is missing or empty`** — задайте обязательную переменную
  окружения и повторите запуск. Пустое значение недопустимо.
- **`undefined variable $name`** — проверьте имя и явное раскрытие через
  `$name`.
  Кавычки не включают раскрытие переменных.
- **ошибка разбора с номером строки** — сначала исправьте синтаксис всего
  файла. yesh не начинает выполнение частично разобранного сценария.
- **отказ внешней команды** — проверьте её отдельно теми же аргументами,
  права доступа, наличие пути и состояние системы. `else` обрабатывает только
  ненулевой код возврата команды, которая действительно запустилась.
- **отказ в доступе** — не добавляйте `sudo` внутрь сценария автоматически.
  Сначала решите, в каком окружении должен выполняться весь сценарий, затем
  отдельно проверьте план и обычный запуск.

## 18. Куда идти дальше

Учебник не превращает yesh в оболочку. В базовую модель не входят переход в
другой каталог через `cd`, функции, подстановка вывода команды и автоматическое
добавление `sudo`. Уже выполненные действия также не откатываются сами по себе.

  редиректах и остановке процессов;

  поддерживаемых форм.
