# Длительные операции, прогресс и состояние

Статус: проектирование следующего слоя; произвольный timeout и устойчивое
возобновление пока не являются возможностями языка.

## Что работает сейчас

Обычная внешняя команда или конвейер получает пять минут, затем отменяется
с остановкой группы и ожиданием прямых детей. Это не общий бюджет скрипта.
`pv`, rsync и rsnapshot остаются внешними программами. Потоки передаются
без накопления всего stdout в памяти; stderr идёт отдельно.

```yesh
tar -cf - -- source | pv --numeric --bytes | gzip > partial
mv -- partial archive
```

Сравнение с Bash: та же команда с `set -o pipefail` и кавычками вокруг переменных.
Правило: продвижение данных и успешное завершение — разные факты.
Ошибка `pv`, tar или gzip останавливает конвейер до публикации архива.
Ошибка: пустой stdin или неизвестный общий размер не дают оснований обещать
точный процент и время окончания; можно показать только обработанные байты.

В cron числовой stderr лучше интерактивной перерисовки. Не выводить управляющие
TTY-последовательности в JSON-журнал и не смешивать их с архивом.
[pv manual](https://www.ivarch.com/programs/quickref/pv.shtml).

## Бюджеты следующего слоя

Нужно отдельно задавать время ожидания lock, время операции, отсутствие
активности, общий срок задания и время освобождения ресурсов. Нет данных
в stdout — не обязательно зависание: сжатие, fsync и удалённая сторона
могут работать без вывода. Пауза прогресса не должна сама давать право
безопасно перезапустить произвольную команду.

Точный синтаксис ещё не выбран; специальных переменных, тайно меняющих
таймаут, не вводим. Бесконечное ожидание не становится умолчанием.
Пакетная транзакция, задание systemd и работа snapd требуют своих способов
отмены: убийство CLI не доказывает остановку работы менеджера.

Наблюдаемое длительное задание должно иметь имя/ID, владельца, источник
отмены, границу процессов и итог с признаком частичного результата.
Это развитие [job model](job-model.ru.md), а не неявный фон через `&`.

## Три разных вида данных

1. Журнал событий — последовательность событий с временем и результатами;
   для машинного чтения подходит JSON Lines с ограничением размера записи.
2. Снимок состояния — маленький версионированный документ текущего задания.
3. Точка возобновления — проверенный прикладной этап с доказательством,
   что его результат можно использовать повторно.

Один JSON-файл не даёт автоматически третий пункт. PID без времени запуска
не идентифицирует прежний процесс; исчезновение процесса не доказывает
готовность архива, установленного пакета или завершённой ротации.

Минимальные поля: версия формата, ID задания, входные параметры без секретов,
проверенные идентификаторы объектов, завершённый этап, состояние отмены/ошибки,
пути частичных результатов и их проверочные сведения.
Неизвестная версия или несогласованные поля — отказ, не догадка.

## Запись и чтение

Будущая штатная запись: проверенный каталог и lock → временный файл с
ограниченными правами → полный JSON → fsync файла → rename в той же файловой
системе → синхронизация каталога, когда поддерживается → повторная проверка.
После ошибки должен быть понятен последний подтверждённый этап; несколько
файлов не становятся атомарной транзакцией от одного rename.

Ограничить размер, глубину, строки и коллекции, отличать пустой/обрезанный/
повреждённый файл. Определить политику повторяющихся ключей: декодер не должен
молча подменять конфликтующее значение. Запретить восстановление команд из
строк состояния и повторный shell-разбор содержимого. Секреты и полный argv
с паролями не записываются как обычные поля.

Ссылки и hard links в пути состояния требуют тех же проверок, что изменение
конфигурации. Read-only режим никогда не чинит повреждённый statefile автоматически.

## Реальные проверки

Сейчас есть [Р.П.П.](practical-examples.ru.md): backup с JSON-отчётом и отмена
задания без публикации ложного успеха. Это прикладной отчёт, не штатный журнал
ядра yesh и не готовый протокол возобновления.

Дальше нужны сценарии сбоя на каждом этапе записи, исчерпанного места,
двух конкурирующих запусков, подмены ссылки, устаревшего PID, изменившихся
входов и повторного старта. Возобновлять можно только операции с определённой
семантикой повторения; никаких автоматических повторов install/mount/restart.
