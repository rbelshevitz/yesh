# Регулярные выражения

Regex — отдельный тип значения yesh, а не кусок shell-текста.

## Один синтаксис

```yesh
error = regex '^(ERROR|FATAL):\s+'

if line matches error:
    echo "found error"
```

Не используем `/pattern/`, `[[ =~ ]]`, `grep -E`-условия, `$1` и вложенные
shell-кавычки. Слово `regex` делает тип значения видимым при чтении.

## Именованные группы

```yesh
address = regex '^(?P<host>[a-z0-9.-]+):(?P<port>[0-9]+)$'
match = line match address

if match:
    echo match.host match.port
```

`match` — обычное структурированное значение с известными полями, не
объектная иерархия. Обращение к несуществующей группе — ошибка с номером строки.

## Замена

```yesh
version = regex '^(?P<name>[a-z-]+)=(?P<value>.*)$'
replace version in settings.conf with name "new-value"
```

Замена по умолчанию только строит diff/plan. Запись требует явного `apply`;
runtime пишет во временный файл в том же каталоге, сохраняет mode/owner и
атомарно заменяет исходник. Regex не должен превращаться в shell-команду.

## Преднамеренные ограничения

- движок MVP — Go `regexp` (RE2), с линейным временем обработки;
- нет lookbehind, backreferences и произвольного кода внутри regex;
- очень длинный pattern и очень большой input ограничиваются runtime;
- вход всегда UTF-8, бинарные файлы требуют явного `binary`;
- для сложного PCRE2 остаётся внешняя команда, например `rg -P`, но её
  результат не становится автоматически доверенным структурированным значением;
- regex не раскрывает секреты в ошибках и `--plan`.

Правило: regex отвечает только за сопоставление и извлечение текста; обход
файлов, изменение файлов, запуск команд и управление процессами имеют отдельные
операции yesh.

## План реализации runtime

Внутри `value` нужен отдельный `regex`-variant с уже скомпилированным
`*regexp.Regexp`; компиляция выполняется при присваивании, поэтому ошибка
pattern указывает на строку yesh и возникает до запуска внешних команд. AST не
должен передавать regex обратно через shell argv.

Для совпадения runtime использует `FindStringSubmatchIndex` и
`SubexpNames`: сначала хранятся индексы в исходной строке, затем по запросу
строятся именованные captures. Это снижает копирование больших строк и даёт
явную точку, где можно ограничить число совпадений. Go API именно так
разделяет поиск и submatch indices, а `Expand` поддерживает шаблоны замен.
[regexp package](https://pkg.go.dev/regexp)

Ограничения runtime:

- pattern максимум 64 KiB;
- один входной record максимум 8 MiB;
- максимум 100 000 совпадений на операцию;
- максимум 64 именованных capture-группы;
- одинаковые имена групп запрещены, чтобы `match.name` был однозначным;
- `FindAll...` не вызывается без лимита `n`;
- потоковые операции используют `bufio.Reader`, а не чтение всего файла в память;
- временный файл для `apply` создаётся рядом с оригиналом, закрывается перед
  rename, а все ошибки cleanup сохраняются в диагностике.

Проверки должны включать: невалидный pattern, UTF-8, пустое совпадение,
перекрывающиеся совпадения, большой record, лимит совпадений, повторяющиеся
именованные группы, отмену операции и ошибку закрытия/rename. RE2 намеренно
отказывается от backreferences и look-around: это сохраняет линейную оценку и
не даёт пользовательскому pattern превратить админский скрипт в DoS.
[RE2 safety rationale](https://github.com/google/re2)
