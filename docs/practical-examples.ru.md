# Р.П.П. — реальные практические примеры

Пример считается рабочим, если его результат проверен: данные восстановлены,
неверная конфигурация не заменила рабочую, прерванное задание не объявлено
успешным. Одного кода выхода недостаточно.

Сценарии проверяют `cmd/yesh/practical_posix_test.go` и
`cmd/yesh/initrd_linux_test.go`.
Тесты используют собственные временные каталоги, не работают с production,
не подключаются к SSH и не перезапускают службы машины.

## Правила кодов выхода практических примеров

Коды выхода ниже — соглашение прикладных примеров, а не дополнительные коды
языка. Они позволяют вызывающему backup/CI-скрипту отличить обычную ошибку от
небезопасного назначения или нехватки ресурса:

| Код | Значение |
| --- | --- |
| `0` | операция завершилась успешно |
| `1` | общая ошибка выполнения |
| `2` | отсутствует исходный или целевой путь |
| `3` | проверка безопасности не пройдена, например не совпал UUID/PARTUUID |
| `4` | не хватает ресурса, например свободного места |

Практический пример должен сохранять выбранный код явно через `exit code`, а
тест должен проверять и код, и диагностический вывод. Не следует сводить все
ошибки к `1`: это скрывает причину от вызывающей автоматизации. Сам язык
принимает явный десятичный код от `0` до `255`; это соглашение не меняет
семантику команд и их собственных кодов.

## Резервная копия с проверкой восстановления

[backup.yesh](../examples/backup.yesh) создаёт tar/gzip во временном имени,
публикует архив только после успеха конвейера и записывает небольшой JSON-отчёт.

```yesh
source = "source"
partial = "backup.tar.gz.partial"
archive = "backup.tar.gz"
tar -cf - -- source | gzip > partial
mv -- partial archive
```

Сравнение с Bash:

```bash
set -euo pipefail
source=source
partial=backup.tar.gz.partial
archive=backup.tar.gz
tar -cf - -- "$source" | gzip > "$partial"
mv -- "$partial" "$archive"
```

Правило: публикация результата следует после успешного завершения всех стадий.
В Go-тесте архив читается через `compress/gzip` и `archive/tar`; сравниваются
имена и байты, включая пробелы и двоичные данные, проверяется контрольная
сумма gzip и JSON-отчёт. Ошибка чтения исходного каталога оставляет прежние
архив и отчёт без изменений. Незавершённый `.partial` не выдаётся за готовый файл.

Этот пример не заменяет политику backup: нет проверки отдельного mount,
свободного места, согласованного снимка изменяющегося источника или атомарной
транзакции «архив + отчёт». Во время сбоя между двумя rename архив может
оказаться новее отчёта. Устойчивое возобновление ещё не реализовано.

## Хранилище: предварительная проверка без изменений

[storage-check.yesh](../examples/storage-check.yesh) проверяет, что точка
назначения действительно находится на смонтированной файловой системе, затем
показывает её источник, свободное место и распределение размера на первом
уровне каталога. Скрипт ничего не монтирует и не изменяет.

```yesh
mountpoint = /backup
if findmnt --target mountpoint:
    findmnt --target mountpoint
    df -P -h -- mountpoint
    du -x -d 1 -h -- mountpoint
else:
    echo "backup mount is missing"
    exit 1
```

Сравнение с Bash: те же утилиты требуют `"$mountpoint"`, а проверка блока
обычно смешивается с `test`, `&&` и настройкой обработки ошибок. В yesh
источник, свободное место и расход диска читаются сверху вниз как один
предварительный этап.

Правила безопасности: `du` не переходит на другие файловые системы (`-x`),
ограничен первым уровнем (`-d 1`) и не следует символьным ссылкам по умолчанию.
Ошибки доступа не считаются нулевым размером. `ncdu` пока остаётся внешней
интерактивной утилитой для ручного осмотра; его вывод не используется как
машинное решение для backup.

Тест проверяет существующий и отсутствующий каталог. Это проверка локального
стенда, а не доказательство правильности mount-политики production-диска.

## Устройство за каталогом: только чтение

[storage-device-check.yesh](../examples/storage-device-check.yesh) строит
диагностический отчёт: `findmnt` показывает файловую систему за путём,
`lsblk` и `blkid` — доступные сведения об устройствах и UUID, `stat` — тип,
права и владельца самого пути.

```yesh
if findmnt --target mountpoint:
    findmnt -no SOURCE,FSTYPE,OPTIONS --target mountpoint
    lsblk --fs --output NAME,TYPE,FSTYPE,LABEL,UUID,PARTUUID,MOUNTPOINTS
    blkid --output full
    stat -c "type=%F mode=%a owner=%U:%G" -- mountpoint
else:
    exit 1
```

Это отчёт внешних утилит, а не автоматический выбор диска. Для типизированной
проверки уже доступны `device by uuid|partuuid` и `require mounted`; ниже
показана также проверка из снимка fstab. Полный вывод lsblk не нужно искать
по подстроке.

[fstab-mount-check.yesh](../examples/fstab-mount-check.yesh) связывает запись
конфигурации с устройством и точным активным mount:

```yesh
mounts = fstab "/etc/fstab"
require mounted /mnt/backup from $mounts
echo "configured backup device is mounted"
```

Что упрощено: не нужно вручную сопоставлять два вывода findmnt, разрешать UUID,
проверять неоднозначность и не путать каталог внутри `/` с отдельным mount.
Требуется одна запись с UUID/PARTUUID и явным типом ФС. При несовпадении
следующий шаг не выполняется; nofail/noauto не скрывают ошибку. `--plan`
откладывает все запросы. Ограничения специальных типов и проверки options
описаны в [storage](storage.ru.md).

Р.П.П. `TestLinuxFstabRealMountBinding` использует искусственный fstab, реальное
устройство и активный root mount WSL; запись для незамонтированного временного
каталога отклоняется. Исходный `/etc/fstab` не меняется. Дубликаты, другой UUID,
тип ФС/major:minor, поддерево и autofs-only проверены на подменённых утилитах,
включая отсутствие публикации успешного результата. Реальный GPT/PARTUUID,
активация automount и boot этим не доказаны.

[storage-identity-check.yesh](../examples/storage-identity-check.yesh) выполняет
такую проверку без разбора вывода:

```yesh
expected_source = "UUID=replace-with-the-real-uuid"
if findmnt --source expected_source --target mountpoint:
    echo "backup filesystem identity is correct"
else:
    echo "backup filesystem identity does not match"
    exit 1
```

Внешний пример с `--target` проверяет содержащую путь ФС, а не обязательно
отдельный mount в этом каталоге; для точного mountpoint используйте
типизированный `require mounted` выше.
`findmnt` принимает `UUID=` и `PARTUUID=` как спецификации источника.
Поэтому несовпадение — это отказ до запуска rsync, а не предупреждение после
записи. Значение UUID должно поступать из проверенной конфигурации или
окружения, а не храниться в примере как настоящий идентификатор. Явная форма
yesh:

```yesh
expected_source = environment YESH_BACKUP_SOURCE
```

Отсутствующее или пустое значение окружения — ошибка. В `--plan` само значение
не показывается.

## Rsync на конкретный диск

[rsync-safe-copy.yesh](../examples/rsync-safe-copy.yesh) объединяет проверки:
исходный каталог, каталог назначения, точная идентичность файловой системы,
свободное место и только затем копирование. При несовпадении UUID/PARTUUID
`rsync` не запускается. Ожидаемый источник читается из
`YESH_BACKUP_SOURCE`, а не хранится в файле.

Это отдельный сценарий для резервного диска. Обычный `rsync-copy.yesh` остаётся
наглядным примером копирования в уже выбранный каталог; он не может сам узнать,
какой внешний диск должен считаться правильным.

Для числового порога свободного места используется отдельное условие yesh:

```yesh
if free_space target at_least 20GiB:
    rsync -a --itemize-changes -- source target
else:
    echo "not enough free space"
    exit 1
```

Размер задаётся целым числом и бинарной единицей `B`, `KiB`, `MiB`, `GiB` или
`TiB`. yesh получает число свободных байтов через `statfs`; текстовый вывод
`df` для арифметики не разбирается.

Коды завершения в этом примере следуют общим правилам практических примеров:

| Код | Значение |
| --- | --- |
| `0` | копирование завершилось успешно |
| `2` | исходный или целевой каталог отсутствует |
| `3` | целевая файловая система не совпала с ожидаемым UUID/PARTUUID |
| `4` | на целевой файловой системе недостаточно места |

Общие правила `exit` описаны в [`control-flow.ru.md`](control-flow.ru.md) и
man-странице.

## rsync: проверка перед копированием, просмотр и копирование

[rsync-preview.yesh](../examples/rsync-preview.yesh) сначала проверяет каталог
назначения, его файловую систему и свободное место, а затем вызывает
`rsync -a --dry-run --itemize-changes -- source target`.
[rsync-copy.yesh](../examples/rsync-copy.yesh) выполняет те же проверки перед
копированием в существующее назначение.

```yesh
source = "source/"
target = "target/"
rsync -a --dry-run --itemize-changes -- source target
```

Сравнение с Bash: `rsync -a --dry-run --itemize-changes -- "$source" "$target"`.
Правило: просмотр не меняет файлы, копирование не добавляет `--delete` молча.
Тест проверяет отсутствие копии после просмотра, точное содержимое после
копирования, сохранность источника и лишнего файла в назначении.

Ошибка выбора назначения опаснее синтаксической ошибки: одного существования
каталога недостаточно. Теперь пример проверяет фактическую файловую систему
через `findmnt` и показывает `df` перед запуском rsync. Это ещё не проверка
ожидаемого UUID внешнего диска и не числовой порог свободного места.
И прогноз rsync может устареть, если файлы изменились между просмотром и запуском.
[rsync(1)](https://download.samba.org/pub/rsync/rsync.1.html).

## rsnapshot: две версии и жёсткие ссылки

[rsnapshot-local.yesh](../examples/rsnapshot-local.yesh) сначала выполняет
`configtest`, затем заданный уровень `daily`.

```yesh
config = "rsnapshot.conf"
rsnapshot -c config configtest
rsnapshot -c config daily
```

Сравнение с Bash: те же argv с `"$config"` и включённой остановкой при ошибке.
Правило: конфигурация проверяется до backup; ненулевой код, включая предупреждение
о частичном переносе, не считается полным успехом yesh.

Go-тест генерирует штатную конфигурацию с табуляцией, `no_create_root=1`,
собственным lockfile и двумя сохраняемыми версиями. После двух запусков
проверяются новое и старое содержимое, общий inode неизменённого файла
и отсутствие оставшегося lock. Системный `/etc/rsnapshot.conf` не используется.

`--relative` rsnapshot сохраняет и подразумеваемые родительские пути.
В тесте граница `/./` ограничивает их собственным исходным каталогом:
не нужно копировать владельца и группу чужого `/tmp`. В реальном плане
эта граница и расположение восстановления должны быть видны, а не меняться
обёрткой молча. Редактирование файла или его прав через hard link может затронуть
несколько снимков — существующие snapshot inode нельзя считать независимыми.
[конфигурация rsnapshot](https://github.com/rsnapshot/rsnapshot/blob/master/rsnapshot.conf.default.in),
[руководство](https://github.com/rsnapshot/rsnapshot/blob/master/docs/HOWTOs/rsnapshot-HOWTO.en.md).

## Конфигурация: проверить до замены

[config-apply.yesh](../examples/config-apply.yesh) показывает небольшую
контролируемую замену:

```yesh
if grep -q '^mode=production$' staged:
    install -m 0640 -- staged next
    mv -- next active
else:
    exit 1
```

Сравнение с Bash: `if grep ... "$staged"; then install ...; mv ...; else exit 1; fi`.
Правило: неверная подготовленная конфигурация не заменяет рабочий файл.
Тест проверяет оба исхода, содержимое и итоговые права `0640`.

`grep` здесь — демонстрационная проверка одного параметра, не универсальный
валидатор приложения. В производственном сценарии нужен штатный валидатор;
необходимо также учитывать владельца, ACL, метки и синхронизацию записи.
Перезапуск службы не является скрытым последствием изменения файла.

## Процессы: read-only снимок nginx

[process-snapshot.yesh](../examples/process-snapshot.yesh) ищет процессы с
точным именем `nginx` и показывает один снимок:

```yesh
nginx = processes where name is "nginx"
show $nginx fields pid uid state rss start_time cgroup
```

Вывод содержит выбранные PID, UID, состояние, RSS в байтах, время запуска и cgroup. Полный
набор также включает PPID, PGID, SID и имя. Это не аналог `pkill`: yesh не посылает
сигналы и не изменяет процессы. В WSL с запущенным nginx пример показал
master и четыре worker-процесса в одном systemd cgroup.

Точный поиск важен: regex, поиск по полной командной строке и управление
процессами будут отдельными возможностями с дополнительными проверками.

Итог по RSS читается напрямую:

```yesh
summarize $nginx memory rss
```

Результат содержит число процессов, сумму, максимум и целочисленное среднее
в удобных бинарных единицах; точное число байтов указывается в скобках.
В проверке с пятью процессами nginx сумма составила `21.80MiB`
(`22863872` байта). Это оценка RSS, а не точный объём уникальной физической памяти.

Для проверки бюджета без shell-арифметики используется:

```yesh
if memory $nginx rss at_most 512MiB:
    echo "nginx RSS is within the budget"
else:
    summarize $nginx memory rss
    exit 1
```

Полный пример — [process-memory-check.yesh](../examples/process-memory-check.yesh).

На Rocky Linux 9.8 все три process-примера были запущены напрямую. В sandbox
nginx отсутствовал, но на host Rocky yesh увидел пять процессов nginx в
`/system.slice/nginx.service`: `PROCESS_COUNT=5`, `RSS_TOTAL=15.46MiB`
(`16211968` байт), `RSS_MAX=3.37MiB` и `RSS_AVERAGE=3.09MiB`. Это также
подтвердило чтение UID, состояния и systemd cgroup. Отдельные тесты с
fixture-процессами проверяют точное имя, поля снимка, RSS-агрегацию и границы
`/proc`.

## Процессы, службы и deploy

Реальный CLI получает TERM во время незавершённой операции. Проверяется
исчезновение её группы, сохранение частичного файла, отсутствие публикации
готового результата и неизменность прежнего файла состояния.

[deploy.yesh](../examples/deploy.yesh) и
[service-check.yesh](../examples/service-check.yesh) выполняются с тестовыми
`rsync` / `ssh` / `systemctl`, которые фиксируют argv и коды ответа.
Это проверяет безопасную передачу аргументов, порядок вызовов и остановку
после неактивной службы. Это не проверка настоящего SSH или systemd bus.

Типизированные примеры делают более важные гарантии явными:
[service-status.yesh](../examples/service-status.yesh) читает фиксированный
allowlist свойств, [service-restart.yesh](../examples/service-restart.yesh)
после restart проверяет точный возвращённый unit и `ActiveState`, а
[service-wait.yesh](../examples/service-wait.yesh) без изменения службы
опрашивает состояние до конечного timeout и сообщает последнее состояние при
отказе, а
[service-journal.yesh](../examples/service-journal.yesh) ограничивает интервал,
число записей и объём вывода, требуя корректный JSON и чистый stderr.
Fixture-тест проверяет точный argv, успешные status/restart/wait, отказ
postcondition и timeout wait, JSON-журнал и `--plan` без внешнего вызова.
Настоящие systemd bus и journal
этим fixture не подтверждаются и требуют отдельного opt-in запуска на host.

Для такого запуска подготовлен
сценарий [`scripts/yesh-fixture-test.sh`](../scripts/yesh-fixture-test.sh).
Он использует только уникальные временные имена в `/run/systemd/system`,
сначала отказывается перезаписывать существующий файл, автоматически удаляет
fixture через `trap` и проверяет также три отрицательных случая: `oneshot`
без `RemainAfterExit`, timeout в состоянии `activating` и аварийный restart с
`Result=exit-code`/ненулевым `ExecMainStatus`.

Отдельно выполнен opt-in прогон на отдельном Linux стенде с systemd 252:
`service-status.yesh` и `service-wait.yesh` подтвердили
`systemd-journald.service` как `loaded/active/running`, а
`service-journal.yesh` корректно завершился с пустым журналом. Для
`service-restart.yesh` выполнен только с `--plan`; реальный перезапуск
production-службы не проводился. В его команде указано имя disposable-unit из fixture; fixture
создаёт и удаляет этот unit в `/run`. Manager на стенде сообщил `degraded`,
поэтому это проверка
конкретного доступного systemd/journal, а не утверждение, что вся машина
здорова.

Различие отказов намеренное: неактивная служба после успешного `systemctl
restart` — ошибка yesh; пустой journal-запрос успешен и означает отсутствие
подходящих записей; непустая диагностика или неверный JSON — ошибка, а не
частичный отчёт.

[ssh-health.yesh](../examples/ssh-health.yesh) проверяет список узлов через
`ssh` с явными настройками порта, `BatchMode` и timeout, собранными в одном
списке argv. В тесте подменённая `ssh` фиксирует
argv и порядок `hostname`/`uptime`; реальные ключи и пароли не читаются.

[scp-copy.yesh](../examples/scp-copy.yesh) передаёт один артефакт через `scp`
с явным назначением и теми же ограничениями, собранными в списке argv. Перед
передачей yesh проверяет наличие локального файла-источника; при его отсутствии `scp`
не запускается. Тест проверяет точный argv;
передача на отдельный удалённый узел проверяется только в окружении пользователя.

Дополнительно пользователь выполнил этот сценарий через локальный loopback
SSH/SCP с ключевой авторизацией: `--plan` показал `scp` с раскрытыми argv,
команда завершилась успешно, а `cmp` подтвердил совпадение исходного и
полученного файла. Затем тот же SCP-сценарий был выполнен на отдельную машину
отдельный Rocky Linux тестовый узел в `/tmp/yesh-test/`, а SHA-256 исходного и удалённого
`go.mod` совпал. Это подтверждает реальную передачу через SSH, но не заменяет
тест восстановления из backup или обработки частично записанного результата.

Для будущей диагностики процессов нужны отдельные Р.П.П.:

- список процессов службы с PID, временем запуска, PGID и cgroup;
- точный выбор и показ цели сигнала, защита от повторного использования PID;
- отмена собственного задания без воздействия на соседнюю группу;
- завершившийся лидер с оставшимися потомками и процесс, покинувший группу;
- отказ в доступе к чужому процессу без попытки повышения прав.

## pv и зависимости

Файлы примеров исполняемые, но не все готовы к запуску на произвольной
машине. Пометка **environment-dependent** в начале файла означает зависимость
от локальной службы, mount, `/proc`, SSH или конфигурации. Пометка
**fixture-dependent** означает, что нужен описанный тестовый fixture.
Перед реальным запуском замените placeholders: `web-1`, `/backup`, примерные
UUID и удалённые пути не являются рабочими значениями.

| Группа | Примеры | Что требуется |
| --- | --- | --- |
| Самодостаточные/fixture-тесты | `hello`, `backup`, `config-apply`, `rsync-*`, `initrd-module-check` | временные файлы или описанный fixture |
| Read-only проверки хоста | `process-*`, `mount-check`, `storage-*`, `fstab-*`, `journal-report`, `service-check` | Linux `/proc`, mount/fstab, journal/systemd или реальная точка монтирования |
| Удалённые/настроечные | `ssh-health`, `scp-copy`, `deploy`, `rsnapshot-local` | SSH trust/agent, удалённая цель или подготовленный config |

Go-тест проводит двоичные данные через `pv --numeric --bytes`, отдельно
проверяя stderr прогресса и stdout/файл данных. Прогресс не попадает в архив.
Показанный счётчик байтов сам по себе не доказывает успешное завершение backup.
[pv manual](https://www.ivarch.com/programs/quickref/pv.shtml).

Запуск набора:

```bash
export GOCACHE="$PWD/.gocache"
export GOMODCACHE="$PWD/.gomodcache"
go test -v ./cmd/yesh -run TestPOSIXPractical -timeout=90s
```

Требуются tar, gzip, grep, install, mv, rsync, pv и rsnapshot.
Для Ubuntu/Debian дополнительные пакеты: `rsync pv rsnapshot`.
При отсутствии команды тест прямо сообщает, какой пакет установить, и
помечает сценарий пропущенным. Linux CI устанавливает эти зависимости явно.

На данном WSL реальный набор с rsync, pv и rsnapshot прошёл после установки
пользователем недостающих пакетов. Тесты не подтверждают backup реального
сервера, загрузку ядра, монтирование или сохранность данных при потере питания.

## Модуль в initramfs: реальный просмотр подготовленного образа

[initrd-module-check.yesh](../examples/initrd-module-check.yesh) вызывает
установленный `lsinitramfs` и проверяет точный путь модуля через grep.
Тест `TestLinuxPracticalInitrdModuleManifest` создаёт настоящий архив newc
через cpio, сжимает его gzip или zstd и передаёт реальному lsinitramfs.
Проверяются пять случаев: правильный путь в обоих форматах сжатия,
другая версия ядра, отсутствие модуля и повреждённый образ.

```yesh
image = "test-initrd.img"
modulefile = "usr/lib/modules/6.1.0-yesh-test/kernel/drivers/nvme/host/nvme.ko"
lsinitramfs image | grep -F -x -- modulefile
```

Сравнение с Bash: тот же конвейер с `"$image"`, `"$modulefile"` и pipefail.
Правило: точная проверка манифеста не должна принимать модуль другого ядра
или ошибку чтения образа за успех.

Содержимое `.ko` в тесте — явно обозначенный фиктивный файл. Это испытание
архива/сжатия/инструмента/конвейера, не совместимости драйвера, sysfs-привязки
и не загрузки ядра. Распознавание встроенных драйверов и зависимостей остаётся
планом [диагностики устройств](boot-and-device-debug.ru.md).

Нужны пакеты `initramfs-tools-core cpio zstd` плюс gzip и grep.
Пользователь установил их; пять случаев прошли без записи в `/boot`.
