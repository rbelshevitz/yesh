# Итоги исследования наблюдения ресурсов службы

Дата проверки: 1 ноября 2026 года.

Стенд: Debian 12, ядро Linux `6.1.0-49-amd64`, systemd `252`, единая иерархия
cgroup v2. Здесь cgroup —
узел группы управления процессами в ядре. Каждый процесс входит в один узел
иерархии; группы могут быть вложенными, а родительская группа может учитывать
свои дочерние группы.

## Что проверяли

Целью было проверить, какие свидетельства о службе может безопасно собрать
yesh на одной Linux-машине:

- путь cgroup и состав процессов службы;
- текущую память, резидентную память процессов (RSS), PSI, CPU и OOM-счётчики;
- доступность блочного учёта через `io.stat`;
- конечный замер с несколькими точками и сохранением JSON-состояния;
- различие между отсутствующей метрикой и нулевым значением.

Проверка не меняла nginx, его лимиты или содержимое постоянной конфигурации.
Единственное временное изменение — включение `IOAccounting` для проверки
контроллера I/O. Временная служба для нагрузки после завершения удалила свой
каталог.

## Исходное состояние nginx

Для `nginx.service` systemd сообщил:

```text
ControlGroup=/system.slice/nginx.service
InvocationID=1cf717120ee8429299078a316af8c2bf
ActiveState=active
MainPID=497
```

В группе процессов службы были доступны только контроллеры `memory pids`. Файла `io.stat` не
было, а `cpu.stat.local` также отсутствовал. При этом были доступны память,
процессы, RSS, PSI, `memory.events` и `memory.events.local`.

Снимок yesh показал:

```text
process_count=3
rss_bytes=9170944
memory_current=6721536
memory_max=max
oom=0
oom_kill=0
io_stat_available=unavailable
observation=partial
```

Результат `partial` здесь правилен: отсутствие контроллера не означает нулевую
нагрузку. Оно означает, что данное свидетельство не было доступно.

RSS процессов берётся из `/proc/<pid>/stat`. Это оценка числа резидентных
страниц, а не точный счёт физической памяти: общие страницы могут учитываться
у нескольких процессов, и ядро прямо предупреждает о неточности этого значения.

## Включение учёта I/O

Для проверки использовался скрипт
[`enable-nginx-io-accounting.sh`](../../scripts/enable-nginx-io-accounting.sh):

```bash
sudo /tmp/enable-nginx-io-accounting.sh
```

Скрипт выполняет:

```bash
systemctl set-property --runtime nginx.service IOAccounting=yes
```

После этого контроллеры nginx стали `io memory pids`, а
`io_stat_available=yes`. Сам `io.stat` у nginx оставался пустым: браузерная
нагрузка создавала сетевые запросы, но не доказала блочное чтение с диска.
Отдача из page cache и запросы, которые не попали в этот nginx, объясняют, почему
сетевой трафик не обязан увеличивать `io.stat`.

## Положительный I/O-стенд

Для доказательства блочного учёта использовалась временная служба,
запускаемая скриптом
[`start-io-mock-service.sh`](../../scripts/start-io-mock-service.sh):

```bash
sudo /tmp/start-io-mock-service.sh
```

Служба:

- запускается через `systemd-run`;
- получает `IOAccounting=yes`;
- имеет ограничение `RuntimeMaxSec=90s`;
- циклически записывает и читает временный файл;
- после завершения удаляет временный каталог;
- не меняет nginx и постоянные unit-файлы.

Для `yesh-io-mock.service` ядро показало устройство `8:0`:

```text
rbytes=536961024
wbytes=662700032
rios=515
wios=554
dbytes=0
dios=0
```

PSI службы в момент нагрузки:

```text
io.pressure some avg10=57.35 avg60=16.68 avg300=3.81
io.pressure full avg10=57.35 avg60=16.68 avg300=3.81
```

Одно измерение yesh продолжительностью 10 секунд и интервалом 2 секунды
сохранило 6 полных точек:

```text
SERVICE_MEASURE ... samples=6 complete=true
memory: 70.6 MiB -> 133 MiB
OOM kills: 0
```

После истечения времени служба завершилась с `Result=success`, кодом `0`, а
временный каталог был очищен.

## Выводы для yesh

1. `io` — необязательный контроллер. yesh не должен включать его сам: это
   изменение политики systemd и cgroup всей ветки.
2. `io.stat` нужно читать как счётчики по устройствам `major:minor`, а не как
   одно число всей службы. Ядро не обещает порядок строк.
3. Отсутствие `io.stat`, `cpu.stat.local` или отдельных полей должно быть
   явным `unavailable`; нельзя подменять его нулём.
4. PSI показывает давление, но само по себе не доказывает, какой процесс был
   причиной задержки.
5. Браузерная нагрузка годится для проверки сети, но не для доказательства
   блочного I/O. Для последнего нужен управляемый стенд с реальным чтением и
   записью.
6. Один снимок полезен для состояния, но вывод о периоде требует конечного
   измерения с несколькими точками и сохранёнными исходными данными.
7. Снимок cgroup показывает узел, непосредственно входящие в него процессы и
   охваченные наблюдением вложенные группы; он не доказывает владение
   приложением или идентичность контейнера.

## Что означает cgroup службы в systemd

`ControlGroup=` — это путь к корню cgroup данного блока systemd. Это граница
службы, но не список процессов, застывший в один точный момент, и не обязательно
единственный каталог, в котором находятся её процессы.

Без делегирования systemd владеет поддеревом cgroup и сам управляет размещением
процессов и политикой ресурсов. При `Delegate=yes` systemd передаёт службе
владение поддеревом ниже cgroup службы. Тогда служба может создавать вложенные
группы и перемещать в них свои процессы; systemd намеренно не перестраивает
такое делегированное поддерево. Связанная настройка `DelegateSubgroup=`
помещает основной процесс службы в именованную дочернюю группу.

Поэтому yesh считает `ControlGroup=` корнем дерева наблюдения, рекурсивно читает
`cgroup.procs` и отмечает неполный список процессов. Он не предполагает, что
`cgroup.procs` корня содержит всю службу. Ядро может изменить состав группы,
пока читаются эти файлы и `/proc`, поэтому результат собирается за короткий
промежуток времени и не является одной идеально согласованной картиной. Процесс,
который явно успел выйти из дерева, исключается; процесс, вошедший в дерево
после обхода, всё ещё может быть пропущен.

Такое толкование следует из документации systemd о
[`Delegate=`](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)
и правил иерархии
[cgroup v2 в ядре Linux](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

## Проверка вложенной cgroup на Debian-стенде

На Debian-стенде использовалась временная пользовательская служба с
`Delegate=yes`, которая создала дочернюю cgroup. В делегированной ветке были
доступны `cpu memory pids`; после переноса управляющего процесса из родителя
тест включил `cpu` и `memory` для дочернего узла. Счётчики CPU родителя и ребёнка
росли, причём изменение у родителя включало работу вне ребёнка — это согласуется
с иерархическим учётом `cpu.stat`.

Той же пользовательской службе контроллер `io` не выдали. В
`cgroup.controllers` оставались `cpu memory pids`, а `io.stat` был недоступен и
у родителя, и у ребёнка. Добавление `IOAccounting=yes` к временной
пользовательской службе ничего не изменило. Это граница прав и делегирования,
а не доказательство нулевого I/O.

Повторяемый root-стендовый скрипт находится в
[`scripts/yesh-nested-cgroup-rwe.sh`](../../scripts/yesh-nested-cgroup-rwe.sh).
На Debian 12 он включил `cpu io memory` для дочерней группы и выполнил из неё
прямую запись 32 МиБ. Родитель и ребёнок оба показали `wbytes=33554432` и
`wios=32`, а дельта CPU родителя была больше дельты ребёнка. Это подтверждает
на проверенном ядре, что родительский `io.stat`, как и проверенные счётчики CPU
и памяти, включает дочернюю cgroup. Это результат именно данного ядра и
настройки, а не универсальное обещание для любой конфигурации cgroup.

Семантика источников сверялась с документацией ядра
[cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
и systemd
[resource-control](https://www.freedesktop.org/software/systemd/man/252/systemd.resource-control.html).

## Состояние хранения

Первоначальный прототип сохранял один завершённый замер в отдельном `*.json`.
Текущий формат — один ограниченный журнал JSON Lines (`measurements.jsonl`) на каталог
состояния:

- одна завершённая запись JSON на строку;
- один журнал на службу, а не отдельный файл и инод на каждый замер;
- дозапись под блокировкой;
- ограниченный размер записи;
- оборванная последняя строка не делает весь журнал нечитаемым;
- очистка журнала выполняется через временный файл и атомарное переименование;
- старые отдельные `*.json` могут читаться во время перехода.

Это ограничивает расход инодов: два дописанных замера остаются одним
`measurements.jsonl` плюс служебный файл блокировки. При очистке временно
появляется один дополнительный файл; после атомарной замены он удаляется.
Поэтому будущая политика должна ограничивать и размер журнала в байтах, и
число журналов служб, а не только число записей.

Практически необходимое окно истории — не менее 24 часов: запрос
`summarize ... since 24h` не должен терять начало периода из-за очистки. Для
этого хранение должно оставлять 24 часа плюс небольшой запас; очистка старше
этого окна должна быть отдельным явным действием.

В `summarize` добавлены дельты `rbytes`, `wbytes`, `rios`, `wios`, `dbytes` и
`dios` по каждому устройству. Смена набора устройств, недоступность одной из
точек или сброс счётчика помечаются как неполное сравнение; устройства не
сливаются в одно безымянное число.

## Как не повредить журнал JSONL

Журнал JSON Lines (JSONL) не является одним большим JSON-документом и не должен иметь
внешние `[` и `]`. Каждая строка — самостоятельный JSON-объект. Запись считается
завершённой только после записанного перевода строки `LF`.

Правила записи:

1. Сначала полностью собрать и проверить один ограниченный JSON-объект в памяти.
2. Добавить к нему один `LF` и дописать в файл с `O_APPEND`.
3. Для нескольких процессов использовать блокировку yesh; одного `O_APPEND`
   недостаточно как политики владения журналом.
4. Обработать короткую запись, затем вызвать `fsync` файла. Для требования
   сохранности имени после сбоя питания отдельно вызвать `fsync` каталога.
5. Не считать запись опубликованной до `LF`. Если процесс оборвался после части
   JSON или перед `LF`, чтение останавливается на последнем незавершённом хвосте
   и сохраняет предыдущие строки.
6. Полностью записанная, но синтаксически повреждённая строка — это ошибка
   журнала, а не повод молча пропустить данные. Это отличает повреждение от
   обычного оборванного хвоста.

`O_APPEND` атомарно совмещает выбор конца файла и операцию записи на обычной
локальной файловой системе, но не даёт гарантии сохранности после сбоя питания.
Для NFS у `O_APPEND` есть отдельные ограничения, поэтому журнал состояния
следует хранить на локальной файловой системе или явно принимать более слабую
границу доказанного поведения.

Эта схема следует смыслу потоковых JSON-последовательностей: независимые записи
обрабатываются по одной, а оборванная последняя запись не должна делать весь
поток нечитаемым. Формат RFC 7464 использует дополнительный разделитель `RS`
перед каждой записью; yesh пока сохраняет более привычный JSONL с `LF`, потому
что его проще читать обычными Unix-командами. [RFC 7464](https://www.rfc-editor.org/rfc/rfc7464)
