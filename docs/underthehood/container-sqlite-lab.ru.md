# Практический стенд: одноразовая миграция Alpine без Bash

Этот стенд показывает не поддержку SQLite и не замену контейнерной среды.
Он проверяет более узкую идею: yesh может быть явным исполняемым сценарием в
одноразовом минимальном образе, где не требуется писать связующий Bash-код.

Коротко: yesh здесь — не мигратор и не средство управления контейнерами. Это
сценарий, который соединяет предварительную проверку, локальную блокировку,
вызов внешней команды и проверку её результата. База, SQL-миграция и правила
транзакции принадлежат `sqlite3` и приложению; образ, том и ограничения
процесса принадлежат Docker.

Стенд полезен только для одного локального файла базы в одном запущенном
контейнере. Он не отвечает на вопрос «как безопасно мигрировать кластер» и не
выбирает, когда миграцию разрешено выполнять в развёртывании.

## Зачем здесь yesh

Мигратор меняет схему. Docker запускает процесс и подключает том. Но кто
проверяет, что подключён нужный файл, передаёт точные аргументы и подтверждает
результат? Обычно эту часть пишут на Bash.

Именно здесь возникает риск. Ошибка в кавычках меняет аргумент. Ошибка в
порядке шагов запускает мигратор слишком рано. Успешный код внешней команды ещё
не доказывает, что схема получила нужное изменение.

yesh делает этот контракт видимым:

1. проверяет входные условия;
2. задаёт порядок и локальную блокировку;
3. показывает внешний `argv` в `--plan`;
4. проверяет результат и возвращает ошибку.

yesh не управляет версиями схемы и не защищает кластер. База, мигратор и
система развёртывания отвечают за транзакции, распределённую блокировку,
резервную копию, откат и порядок выпуска.

## Что происходит

Контейнер содержит:

- статически собранный `yesh`;
- внешнюю утилиту `sqlite3`;
- файл сценария yesh;
- файл SQL-миграции.

База лежит в подключённом Docker volume. При запуске yesh:

1. проверяет наличие базы и файла миграции;
2. получает локальную неблокирующую блокировку;
3. проверяет, применялась ли миграция;
4. вызывает внешний `sqlite3` с явными аргументами и перенаправлением;
5. проверяет появление ожидаемого столбца;
6. возвращает понятный код ошибки.

Роли разделены:

| Участник | Ответственность |
|---|---|
| yesh | порядок шагов, локальная блокировка, ветвление, точный `argv`, проверка результата, `--plan` и код выхода |
| `sqlite3` и приложение | файл базы, SQL, учёт версий и транзакция |
| Docker | образ, процесс, volume и ограничения контейнера |

yesh не знает модель SQLite и не выполняет SQL сам. Если внешний мигратор
изменится на PostgreSQL, yesh сможет сохранить ту же роль — проверить окружение,
вызвать мигратор и проверить код завершения, — но стенд, проверки готовности и
правила блокировки придётся изменить.

## Что здесь означает «миграция»

Миграция — это не копирование файла базы и не проверка того, что процесс
запустился. Это именованное изменение схемы: в данном примере к таблице
`settings` добавляется столбец `description`, а в таблицу `schema_migrations`
записывается версия `001-add-description`.

Порядок важен:

1. сценарий убеждается, что база и SQL-файл существуют;
2. локальная блокировка не даёт двум процессам этого стенда одновременно
   менять один файл базы;
3. внешний `sqlite3` выполняет SQL внутри `BEGIN`/`COMMIT`;
4. yesh отдельно проверяет наблюдаемый результат — наличие столбца;
5. повторный запуск не выполняет SQL заново, если стенд уже видит таблицу
   учёта миграций.

Это упрощённая учебная проверка. Она показывает порядок действий, но не
является готовым менеджером версий: сценарий проверяет наличие таблицы
`schema_migrations`, а не полный набор версий и не совместимость произвольной
схемы. В настоящем приложении точную версию и порядок миграций должен вести
внешний мигратор, например официальный инструмент приложения. yesh может
дождаться базы, проверить файлы и окружение, вызвать этот инструмент с явными
аргументами и проверить его код завершения, но не должен подменять его моделью
схемы.

Отрицательный файл специально добавляет столбец, а затем вызывает несуществующую
функцию. Из-за `.bail on` `sqlite3` останавливается на ошибке; `ROLLBACK`,
связанный с незавершённой транзакцией, не оставляет частичный столбец. Это
доказывает только поведение данного SQLite-запроса и транзакции. Нельзя
переносить его автоматически на PostgreSQL, другой мигратор или миграцию,
которая выполняет необратимое внешнее действие.

## Почему здесь не Bash

Вместо `ENTRYPOINT ["sh", "-c", "..."]` образ запускает yesh в exec-форме.
В сценарии нет ручного word splitting, скрытых кавычек, `trap`, `set -e` или
неявного объединения кода ошибок. Внешний `sqlite3` остаётся видимым в плане.

Сборка в WSL2 выполнялась с `docker build --network host` только потому, что
обычный build-контейнер не разрешал DNS для `proxy.golang.org` и зеркала
Alpine. Это особенность стенда, а не требование yesh.

Стенд можно повторить так:

```sh
docker build --network host -f Dockerfile.sqlite-lab -t yesh-sqlite-lab .
docker volume create yesh-sqlite-lab-data
docker run --rm -i --read-only --network none --cap-drop=ALL \
  --entrypoint sqlite3 \
  -v yesh-sqlite-lab-data:/data \
  yesh-sqlite-lab /data/app.db < examples/container-sqlite-initial.sql
docker run --rm --read-only --network none --cap-drop=ALL \
  -e YESH_DB=/data/app.db \
  -e YESH_MIGRATION=/app/migration.sql \
  -e YESH_LOCK=/data/migration.lock \
  -v yesh-sqlite-lab-data:/data \
  yesh-sqlite-lab
```

Для сравнения, в Bash пришлось бы вручную соединить проверки, блокировку,
коды ошибок и SQL-вызовы примерно так:

```sh
if test -f "$db" && test -f "$migration"; then
    if mkdir "$lock" 2>/dev/null; then
        trap 'rmdir "$lock"' EXIT
        if ! sqlite3 "$db" 'select ...' | grep -qx 1; then
            sqlite3 "$db" < "$migration" || exit $?
        fi
        sqlite3 "$db" 'select ...' | grep -qx 1 || exit 4
    else
        exit 5
    fi
fi
```

Это не попытка объявить Bash-код неправильным. Смысл сравнения в том, что в
yesh порядок и границы аргументов являются частью языка, а вызов `sqlite3`
остаётся обычным внешним вызовом.

## Четыре доказательства

- Положительный запуск применяет миграцию и подтверждает новый столбец.
- Повторный запуск видит таблицу миграций и не выполняет её снова.
- Отрицательная миграция завершается ошибкой. `.bail on` не даёт SQLite
  продолжить SQL-файл после ошибки; проверка подтвердила отсутствие частичного
  столбца.
- `--plan` показывает блокировку, внешние `argv`, перенаправление и обе ветви,
  но не запускает `sqlite3` и не меняет volume.

Для передачи начальной SQL-схемы через stdin нужен `docker run -i`; без `-i`
контейнер может завершиться успешно, оставив volume пустым. Это относится к
команде подготовки стенда, а не к yesh-сценарию.

## Граница доказанного

Стенд подтверждает только одноразовую операцию на Alpine 3.24 с локальным
файлом SQLite в именованном Docker-томе на Linux/amd64. Он не подтверждает
Kubernetes `Job`, PostgreSQL, распределённую блокировку, CSI/NFS, `fsGroup`,
хранилище без root или универсальную работу в образе без оболочки.

`with lock` защищает только конкурирующие локальные запуски на этом доступном
пути. При нескольких узлах единственный запуск миграции должен обеспечиваться
базой, мигратором или внешним `Job`.

В Linux yesh реализует эту блокировку через `flock` на открытом файловом
дескрипторе. Ядро освобождает блокировку при завершении процесса, в том числе
после `SIGKILL`. Файл по пути блокировки может остаться, но его наличие не
означает, что процесс всё ещё удерживает блокировку. Этот стенд пока не
проверяет убийство процесса или аварийное завершение контейнера; для этого
нужен отдельный тест «прерывание → повторный запуск».

Локальная блокировка также не делает миграцию повторяемой сама по себе. За
повторяемость отвечает учёт применённых версий и поведение внешнего мигратора;
за откат — транзакции базы и ограничения конкретной миграции. yesh отвечает за
то, чтобы не запускать внешний вызов при проваленной предварительной проверке,
показать его в `--plan` и не скрыть его код ошибки.
