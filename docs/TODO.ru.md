# План развития yesh

Порядок приоритетов: читаемость → защита от дурака → корректность POSIX →
удобство → расширение возможностей.

## Рабочая точка

Концепция: читаемая Unix-автоматизация на Go, без исторических ловушек Bash.
Команды и конвейеры остаются естественными; строки и списки различаются.
Декларативные удобства — требования и желаемое состояние небольших ресурсов,
с планом изменений и проверкой результата. Они не превращают yesh в
универсальную систему управления конфигурацией.

Принято:

- Смену обозначения переменных отложить; спорный синтаксис не внедрять.
- Сначала укреплять исполнение, единый разбор значений и диагностику;
  затем добавлять предметные операции по практической необходимости.
- Запрет известных опасных форм команд — вспомогательная проверка,
  а не изоляция произвольного внешнего кода.
- Не исправлять отказ доступа скрытым sudo, снятием защитных атрибутов,
  отключением SELinux/AppArmor или ослаблением системных настроек.
- В документации отделять работающие возможности от проекта будущего интерфейса;
  man-страницы yesh поддерживать на русском и английском, план развития — по-русски.
- Публичное позиционирование должно быть видно сразу: yesh — это Bash без
  исторической синтаксической сложности, а главный критерий — читаемость
  чужого скрипта сверху вниз.
- Публичные README и runnable-примеры — на английском; русские проектные
  документы и русская man-страница остаются отдельным слоем документации.
- Пример считается удачным только если yesh заметно упрощает чтение или
  защищает от типичной ошибки Bash. Простая команда `rsync` сама по себе
  не является доказательством преимущества yesh.

Ближайшие шаги:

1. При возвращении к длительным операциям реализовать согласованный
   `--command-timeout` (пользователь отложил реализацию); затем определить
   устойчивый протокол состояния без обещания автоматического повтора.
2. Свести встроенные команды к одной модели исполнения и добавить `cd` /
   окружение, сохранив границы строк, списков, аргументов и каналов.
3. Реализовывать предметные операции только после читающей диагностики:
   процессы/права, systemctl/sysconfig/sysctl, устройство/модуль/initrd.

Ограничения среды: WSL2, systemd bus недоступен, cgroup v2 только для чтения;
UID 1000 без эффективных capabilities, `NoNewPrivs=1`, seccomp включён.
SELinux/securityfs не видны; это не доказывает отключение защиты на хосте.
Go 1.27 недоступен: локальные проверки используют Go 1.22.2 с временным
`/tmp/yesh-posix.mod`; требование проекта не менялось.

Последний checkpoint:

```text
Цель: сделать yesh очевидно читаемее Bash на первом экране и в runnable-примерах.
Сделано: POSIX/runtime hardening; README с заметным Bash-сравнением; английские
публичные примеры; read-only process/journal/mount/SSH health checks; MIT,
CI и .gitignore отправлены в GitHub.
Решения: обозначение переменных не менять; проектируемые модули не выдавать
за готовые; пример без заметного выигрыша читаемости не считать showcase.
Открыто: English quickstart; объяснение выигрыша каждого примера; затем
match с именованными regex-группами, структурированная диагностика и builtins.
Следующий шаг: после компактирования написать English quickstart Bash → yesh
с явным разбором читаемости, argv и поведения при ошибке.
Проверки: go test -trimpath ./... — PASS; новые примеры разобраны через
--plan; последний push — 897a07e, рабочее дерево было чистым до этой правки.
```

- [ ] Слабые примеры, где yesh лишь повторяет одну внешнюю команду без
  заметного выигрыша читаемости или безопасности, заменить или пометить
  как минимальные примеры передачи аргументов.
- [x] Добавить короткий [English quickstart](quickstart.md): Bash-сценарий →
  yesh-сценарий → объяснение границ и поведения при ошибке.
- [x] Добавить русскую версию quickstart для локальной разработки и ревью.
- [ ] Принимать новые синтаксические возможности только после примера,
  который делает административный сценарий легче читать, проверять и
  безопасно повторять.

В общем прогоне агента тест с двумя UID пропущен из-за непривилегированной
среды. Затем пользователь отдельно запустил `TestPOSIXStickyForeignEntries`
с повышенными правами и подтвердил PASS, включая remove и rename.
Проверено также успешное удаление после снятия sticky-bit.
Детектор гонок, go vet, сборка с `-trimpath -buildvcs=false`,
проверки со случайными входами и отображение обеих man-страниц прошли.
Тестовые бинарные файлы собраны для macOS и Windows; это проверка сборки,
а не выполнения на этих ОС. Проверки systemd/cgroup/SELinux и изменения
атрибутов `+i/+a` на реальном защищённом объекте ещё не выполнены.
Пользователь установил pv, rsnapshot, lsinitramfs, cpio и zstd; соответствующие
Р.П.П. прошли с реальными утилитами. Образы initramfs искусственные,
с фиктивными `.ko`; загрузка ядра и привязка устройства этим не доказаны.

Основные вехи текущего этапа закрыты: полировка условий/завершения,
проверки процессов и конвейеров, Р.П.П., актуальные man и соглашение `*.ru.md`.
Обязательные для продолжения обкатанные правила перенесены в `AGENTS.md`.

  с двумя UID: отдельный запуск пользователя — PASS; после снятия бита удаление разрешено.
- [ ] Сведения о правах, владельце, группах, ACL, атрибутах и причинах отказа в доступе.
- [ ] Желаемые mode/UID/GID одного объекта: план, отсутствие лишних изменений,
  применение через дескриптор и проверка результата.
- [ ] Защита всех компонентов пути, обнаружение подмены объекта,
  отдельная политика символьных и жёстких ссылок.
- [ ] Проверки ACL, capabilities, специальных битов, другого UID и меток
  в изолированном окружении; не выдавать chmod за полную политику доступа.

- [ ] Чтение защитных атрибутов через lsattr / ioctl / statx с различением

- [ ] Учитывать immutable/append-only у файла и родительского каталога

- [ ] Диагностика SELinux: состояние и доступность политики, тип/уровень,

- [ ] Отдельная диагностика AppArmor: профиль процесса, режим и отказы;

- [ ] Учитывать capabilities, пространства пользователей и отображение UID/GID,

- [ ] Снимок настроек `fs.protected_symlinks`, `fs.protected_hardlinks`,
  `fs.protected_regular`, `fs.protected_fifos` без их изменения.
- [ ] Учитывать ro/nosuid/nodev/noexec, существующие открытые дескрипторы,

- [ ] Не путать проверку доступа с разрешением ядра: не строить безопасность

## Системная конфигурация и параметры ядра

- [ ] Уточнить и разделить три формата: unit/drop-in systemd,
  `/etc/sysconfig` / `/etc/default`, параметры ядра sysctl.
- [ ] Для sysconfig определять реального потребителя файла: shell-сценарий
  и `EnvironmentFile=` имеют разные правила. Не исполнять файл через source.
- [ ] Начать с чтения ограниченного формата присваиваний, сравнения и плана;
  неизвестные конструкции сохранять как непрозрачные данные и запрещать их изменение.
- [ ] Обновлять только явно управляемые ключи с сохранением комментариев,
  владельца, прав, меток и проверкой конфликта изменений.
- [ ] Проверять конфигурацию штатным валидатором конкретной службы до применения;
  проверка синтаксиса unit не доказывает правильность конфигурации приложения.
- [ ] Изменение файла не перезапускает службу автоматически: проверка,
  запись, daemon-reload при необходимости, reload/restart и проверка результата —
  отдельные явные действия с видимыми частичными ошибками.
- [ ] Для sysctl сначала чтение конкретных разрешённых ключей, фактические
  значения и происхождение постоянной настройки; без неограниченного `sysctl -a`.
- [ ] Учесть порядок файлов sysctl.d, дубликаты, особенности `/etc/sysctl.conf`
  у procps и различия с systemd-sysctl; не считать эти загрузчики одинаковыми.
- [ ] Применение sysctl — отдельная операция: тип и допустимое значение ключа,
  пространство имён, права, текущая и постоянная настройка, проверка результата.
- [ ] Не менять sysctl защиты, сеть и параметры памяти ради прохождения проверки;
  не вызывать `sysctl --system` или `-p` как скрытый побочный эффект.

Официальные руководства:
[systemctl](https://freedesktop.org/software/systemd/man/latest/systemctl.html),
[systemd.exec](https://freedesktop.org/software/systemd/man/latest/systemd.exec.html),
[sysctl.d](https://www.freedesktop.org/software/systemd/man/latest/sysctl.d.html),
[sysctl(8)](https://man7.org/linux/man-pages/man8/sysctl.8.html).

## SSH и резервное копирование

Следующий прикладной вертикальный срез: безопасная передача и резервное
копирование. Это главный практический маршрут yesh после документации:
SSH → SCP → rsync → rsnapshot, с `pv` для наблюдаемой передачи. Сначала
read-only/preview и локальные тестовые стенды; настоящее удалённое изменение
и восстановление — только отдельная тестовая VM.

- [ ] Для каждой операции показать выигрыш yesh в читаемости: список узлов,
  явные источники/назначения, проверка перед действием, видимая ошибка.
- [ ] Не читать и не хранить приватные ключи, пароли и passphrase; использовать
  обычный `ssh`/`ssh-agent`/`~/.ssh/config`, не подменять хранилище учётных
  данных.
- [ ] SSH: типизированный узел, явный порт/пользователь, timeout и host-key
  policy; запрещать молчаливый `StrictHostKeyChecking=no` и shell-код на узле.
- [ ] SCP: передача одного файла/списка файлов с проверкой локальных путей,
  назначения и частичного результата; не раскрывать секреты в argv/журнале.
- [ ] rsync: `--dry-run`/preview до записи, явный источник и назначение,
  отсутствие неявного `--delete`, проверка mount и свободного места; отдельно
  различать exit code и предупреждения.
- [ ] rsnapshot: `configtest`, lock, mount/source check, свободное место,
  retention и hard-link snapshots; не менять конфигурацию и не ротировать
  копии без явного плана.
- [ ] pv: отделять progress/stderr от двоичных данных, ограничивать pipeline,
  проверять завершение всех стадий и не считать показанный счётчик успехом.
- [ ] Общий `--plan` и отчёт: какие узлы, пути, команды, объём и изменения
  будут затронуты; в плане не выполнять внешние команды.
- [ ] Р.П.П.: локальный стенд, тестовый SSH-сервер, отказ host key/timeout,
  обрыв передачи, заполненное место, незамонтированный backup-диск, lock,
  повторный запуск и проверка восстановления.

## POSIX и переносимость

BusyBox упоминался как пример набора системных команд, а не как цель
интеграции. Отдельный профиль BusyBox/rescue и собственный набор замен
Unix-утилит в текущий план не входят.

- [ ] Проверять наличие внешних системных команд и нужных возможностей;
  при отсутствии явно указывать требуемую утилиту и пакет.
- [ ] Проверять применяемые опции по локальным man и возможностям реализации;
  различия системных утилит не должны менять смысл скрипта молча.
- [x] Рабочее WSL/Linux-окружение для интеграционных тестов
  (ограничения: [отчёт](linux-integration.ru.md)).
- [ ] В WSL подтвердить доступ к systemd, cgroup v2, `/proc` и `/sys`.
- [ ] В WSL установить/проверить procps, kmod, udev, util-linux,
  tmux, screen, rsyslog и средства чтения journal.
- [x] В Linux CI запускать проверки групп процессов, SIGPIPE,
  ограничения времени и файловых дескрипторов.
- [ ] Отдельно пометить тесты, требующие root, CAP_SYS_ADMIN или реального устройства.
- [ ] Условия сборки для Linux: `/proc`, pidfd, cgroup, systemd и kmod.
- [ ] Не считать Windows/WSL полной POSIX-проверкой без указания ограничений.
- [ ] Интеграционные Linux-тесты с управлением cgroup v2/systemd.
- [ ] **Отложено пользователем:** macOS/Darwin. Новую работу и проверки
  этого направления пока не начинать; результаты Linux/WSL не переносить

- [ ] Резервная реализация Windows без обещания POSIX-управления заданиями.
- [ ] TTY, активная группа процессов терминала и PTY — после первой версии,

- [ ] `cd`, окружение, `export` и рабочий каталог как встроенные операции.
