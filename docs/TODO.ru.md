# План развития yesh

Порядок приоритетов: читаемость → защита от дурака → корректность POSIX →
удобство → расширение возможностей.

## Рабочая точка

Концепция: читаемая Unix-автоматизация на Go, без исторических ловушек Bash.
Команды и конвейеры остаются естественными; строки и списки различаются.
Декларативные удобства — требования и желаемое состояние небольших ресурсов,
с планом изменений и проверкой результата. Они не превращают yesh в
универсальную систему управления конфигурацией.

Принято:

- Переменные раскрывать только явной формой `$name`; bare words остаются
  литералами, а `${name}` не добавляется как второй эквивалентный синтаксис.
- То же правило действует для typed-значений: `inspect $mounts`,
  `require mounted путь from $mounts`, `show $processes` и
  `memory $processes rss at_most limit`; голые имена после этих операций
  отклоняются. Объявления и ключевые слова (`for item in $items`) не являются
  ссылками.
- Сначала укреплять исполнение, единый разбор значений и диагностику;
  затем добавлять предметные операции по практической необходимости.
- Запрет известных опасных форм команд — вспомогательная проверка,
  а не изоляция произвольного внешнего кода.
- Не исправлять отказ доступа скрытым sudo, снятием защитных атрибутов,
  отключением SELinux/AppArmor или ослаблением системных настроек.
- В документации отделять работающие возможности от проекта будущего интерфейса;
  man-страницы yesh поддерживать на русском и английском, план развития — по-русски.
- Публичное позиционирование должно быть видно сразу: yesh — это Bash без
  исторической синтаксической сложности, а главный критерий — читаемость
  чужого скрипта сверху вниз.
- Основной публичный README и runnable-примеры — на английском; русская
  версия README, проектные документы и русская man-страница остаются отдельным
  слоем документации.
- Пример считается удачным только если yesh заметно упрощает чтение или
  защищает от типичной ошибки Bash. Простая команда `rsync` сама по себе
  не является доказательством преимущества yesh.

Читающая storage-веха закрыта: чтение fstab и проверка записи по UUID/PARTUUID,
устройству и активному mount реализованы. Следующий шаг этого направления —
контракт readonly mount и отдельный тестовый стенд, без изменения дисков хоста.

## Корпус реальных сценариев Bash

Каталог кандидатов и лицензий: [bash-corpus.ru.md](bash-corpus.ru.md).

До новых языковых возможностей нужен корпус из 20–30 независимых сценариев
администрирования. Для каждого сохраняются источник Bash, адаптация yesh,
`--plan`, положительный и отрицательный тест, а также одно конкретное
объяснение преимущества для ревью. Сценарий не оправдывает новую грамматику,
если он лишь переименовывает внешнюю команду.

- [ ] Отобрать и обезличить сценарии backup/rsync, systemd/journal, storage,
  SSH/SCP и сетевых проверок; не копировать отключение host-key verification,
  скрытый `sudo` или небезопасные destructive defaults.
- [ ] Адаптировать первый набор без расширения языка: проверка service,
  read-only storage preflight, backup preview и SSH health check.
- [ ] Для каждого расхождения с Bash записывать причину: нечитаемая
  конструкция, неявное splitting/quoting, неявная ошибка pipeline или
  отсутствующая безопасная выразительность yesh.
- [ ] Новую встроенную операцию рассматривать только после повторения
  обоснованной проблемы минимум в двух сценариях корпуса.

Остальные направления (длительные операции по-прежнему отложены пользователем):

1. При возвращении к длительным операциям реализовать согласованный
   `--command-timeout` (пользователь отложил реализацию); затем определить
   устойчивый протокол состояния без обещания автоматического повтора.
2. Свести встроенные команды к одной модели исполнения и добавить `cd` /
   окружение, сохранив границы строк, списков, аргументов и каналов.
3. Ранний сетевой слой для preflight перед SSH/backup: IP/CIDR, интерфейсы,
   ARP/neighbours, маршруты, слушающие порты и ограниченная проверка TCP/DNS.
4. Реализовывать остальные предметные операции только после читающей
   диагностики: процессы/права, systemctl/sysconfig/sysctl,
   устройство/модуль/initrd.

Последняя полная проверка выполнена на Rocky Linux 9.8, kernel
`5.14.0-687.59.1.el9_8.x86_64`, Go `1.27.3`, с установленными
`rsnapshot 1.5.1`, `rsync` и `pv`. Пройдены `go test ./...`, `go vet ./...`,
`go test -race ./...` и `go build ./...`. Ранее подробно проверенное WSL2
окружение сохраняется ниже как отдельная историческая проверка storage/systemd.

- [x] Обычный Linux без WSL: Go 1.27, полный `go test`, `go vet`, `go build`,
  race-проверки POSIX/storage/fstab.

## Что yesh уже упрощает

Это не обещание будущего интерфейса, а текущий практический результат:

- чтение условий: обычные `if` и отступы вместо набора `[ ]`, `[[ ]]`,
  `(( ))`, `$` и исторических операторов сравнения;
- передача значений: строки, списки, переменные и regex остаются разными
  типами, без неявного word splitting и повторного разбора значения как кода;
- выполнение: собственный runtime запускает argv напрямую, `--plan` показывает
  раскрытые аргументы, ошибки команд и стадий конвейера не скрываются;
- безопасность повторяемых операций: ограниченные пайплайны, timeout,
  очистка процессов и файловых дескрипторов, проверки перенаправлений;
- администрирование: читаемые проверки mount/UUID/PARTUUID/свободного места,
  SSH/SCP, rsync без неявного `--delete`, а также read-only снимки процессов
  и суммирование их RSS без ручного разбора `ps`/`awk`.

Практический критерий: yesh уже делает сценарий легче читать и проверять,
но пока не заявляет встроенные CIDR/net-tools, полноценный systemd API,
TTY/PTY, typed SSH nodes или управление чужими процессами.

### Критерий читаемого публичного проекта

- [x] README сразу показывает формулу «Bash without the historical syntax
  complexity» и сравнивает конкретные конструкции Bash и yesh.
- [x] Публичные runnable-примеры переведены на английский.
- [x] Добавлены только примеры, исполняемые текущим runtime: процессы,
  journal, read-only mount-проверка и SSH health check.
- [x] Р.П.П. предварительной проверки хранилища без изменений: `findmnt`,
  `df` и ограниченный `du` для точки назначения; без монтирования,
  размонтирования, удаления и перехода между файловыми системами.
- [ ] Для каждого примера в README или сопроводительной документации явно
  объяснено, что именно yesh упрощает по сравнению с Bash.
- [ ] Слабые примеры, где yesh лишь повторяет одну внешнюю команду без
  заметного выигрыша читаемости или безопасности, заменить или пометить
  как минимальные примеры передачи аргументов.
- [x] Добавить короткий [English quickstart](quickstart.md): Bash-сценарий →
  yesh-сценарий → объяснение границ и поведения при ошибке.
- [x] Добавить русскую версию quickstart для локальной разработки и ревью.
- [x] Проверять код quickstart EN/RU запуском и сверять с исполняемым примером:
  доступные/неактивные службы, недоступный/потерянный bus, отсутствие команды,
  сигнал, списки, exists/exit, полный поток и plan без внешних программ.
- [ ] Принимать новые синтаксические возможности только после примера,
  который делает административный сценарий легче читать, проверять и
  безопасно повторять.

В общем прогоне агента тест с двумя UID пропущен из-за непривилегированной
среды. Затем пользователь отдельно запустил `TestPOSIXStickyForeignEntries`
с повышенными правами и подтвердил PASS, включая remove и rename.
Проверено также успешное удаление после снятия sticky-bit.
Детектор гонок, go vet, сборка с `-trimpath -buildvcs=false`,
проверки со случайными входами и отображение обеих man-страниц прошли.
Тестовые бинарные файлы собраны для macOS и Windows; это проверка сборки,
а не выполнения на этих ОС. Проверки systemd/cgroup/SELinux и изменения
атрибутов `+i/+a` на реальном защищённом объекте ещё не выполнены.
Пользователь установил pv, rsnapshot, lsinitramfs, cpio и zstd; соответствующие
Р.П.П. прошли с реальными утилитами. Образы initramfs искусственные,
с фиктивными `.ko`; загрузка ядра и привязка устройства этим не доказаны.

Основные вехи текущего этапа закрыты: полировка условий/завершения,
проверки процессов и конвейеров, Р.П.П., актуальные man и соглашение `*.ru.md`.
Обязательные для продолжения обкатанные правила перенесены в `AGENTS.md`.

## Сеть и CIDR

Сетевой слой нужен прежде всего для читаемых preflight-проверок перед SSH,
SCP и rsync, а не для замены `iproute2` или настройки сети из скрипта.
Это один из первых практических слоёв после текущей документационной и
диагностической работы.

- [ ] Типизированные IPv4/IPv6-адрес и CIDR-префикс на стандартном
  `net/netip`: строгий разбор, нормализация, `contains` и явное различение
  IPv4, IPv6 и IPv4-mapped IPv6; без ручной арифметики масок.
- [ ] Понятное условие принадлежности адреса сети с отрицательным примером
  и ошибками для неверной маски, адреса или смешения семейств.
- [ ] Read-only отчёт интерфейсов и адресов через проверенный вызов `ip`;
  не скрывать отсутствие команды, отказ доступа или неполный результат.
- [ ] Read-only ARP/neighbour-отчёт: IP, MAC, состояние и интерфейс;
  не считать отсутствующую запись доказательством недоступности узла.
- [ ] Read-only таблица маршрутов и слушающих TCP/UDP-портов через `ip`
  и `ss`; ограничить объём вывода и не парсить нестабильный декоративный
  текст без явного формата.
- [ ] Ограниченные проверки DNS, TCP-порта и ICMP с явными timeout/count;
  не считать отсутствие ICMP доказательством недоступности узла.
- [ ] Зафиксировать семантику проверок: нормальный отрицательный результат
  (`порт закрыт`, `адрес не входит в CIDR`) даёт `false`; отсутствие утилиты,
  timeout, отказ доступа или повреждённый ответ являются ошибкой выполнения.
  Встроенные проверки не вводят произвольную таблицу кодов выхода; итоговый
  `exit` и его код явно выбирает автор сценария.
- [ ] Безопасность первой версии: не добавлять встроенные операции изменения
  адресов, маршрутов, firewall, namespace или состояния интерфейса.
- Старые команды пакета `net-tools` (`ifconfig`, `route`, `arp`, `netstat`)
  не встраивать и не делать обязательными; сначала использовать современные
  `ip`/`ss` из iproute2 с проверенными аргументами.
- Новые сетевые Go-зависимости не нужны для CIDR; библиотеку netlink
  рассматривать только если внешние `ip`/`ss` перестанут давать устойчивый
  и проверяемый интерфейс.

## Текст и файлы

- [ ] Потоковый `search` с ограничениями размера входа, записей и совпадений.
- [ ] `replace` только через план и сравнение изменений, затем явный `apply`.

## Права и владельцы файлов

SELinux, AppArmor и контексты — **опциональный Linux-слой**, не часть базового
POSIX/MVP. Его проверять и реализовывать только при наличии соответствующей
системы защиты и отдельного изолированного стенда; отсутствие `securityfs` или
политики в WSL не считать ни успехом, ни отказом.

- [x] [Проектирование прав](permissions.ru.md): chmod/chown, ссылки, ACL,
  специальные биты, умолчания и ограничения файловых систем.
- [x] Проверки внешних chmod/chown на собственных временных файлах и создания при umask 077.
- [x] Sticky-bit каталогов: отдельное описание, установка/снятие и сохранение `01777`.
- [x] Проверить удаление/переименование чужих записей в sticky-каталоге
  с двумя UID: отдельный запуск пользователя — PASS; после снятия бита удаление разрешено.
- [ ] Сведения о правах, владельце, группах, ACL, атрибутах и причинах отказа в доступе.
- [ ] Желаемые mode/UID/GID одного объекта: план, отсутствие лишних изменений,
  применение через дескриптор и проверка результата.
- [ ] Защита всех компонентов пути, обнаружение подмены объекта,
  отдельная политика символьных и жёстких ссылок.
- [ ] Проверки ACL, capabilities, специальных битов, другого UID и меток
  в изолированном окружении; не выдавать chmod за полную политику доступа.
- [ ] Отдельный ограниченный обход дерева без неявного `-R` и перехода монтирований.
- [x] Изучить `chattr(1)`: immutable `+i` и append-only `+a` — атрибуты
  файловой системы Linux, а не обычные биты chmod; поддержка зависит от ФС.
- [ ] Чтение защитных атрибутов через lsattr / ioctl / statx с различением
  «не установлен», «не поддерживается» и «недоступно». Никакого скрытого `chattr -i/-a`.
- [ ] Учитывать immutable/append-only у файла и родительского каталога
  перед записью, переименованием, удалением, ротацией и атомарной заменой.
- [x] **Опционально:** изучить SELinux: контекст процесса и файла, фактическая и ожидаемая
  метка, различие временного chcon и постоянных правил semanage fcontext.
- [ ] **Опционально:** диагностика SELinux: состояние и доступность политики, тип/уровень,
  AVC-сообщения с ограничением вывода, read-only сравнение ожидаемых меток.
- [ ] **Опционально:** явный план перемаркировки; не запускать restorecon/chcon/semanage,
  setenforce или генерацию разрешающей политики как скрытое исправление.
- [ ] **Опционально:** отдельная диагностика AppArmor: профиль процесса, режим и отказы;
  не выдавать профиль за SELinux-контекст и не отключать его автоматически.
- [ ] Учитывать capabilities, пространства пользователей и отображение UID/GID,
  no_new_privs и seccomp; root и mode `0777` не гарантируют доступ.
- [ ] Снимок настроек `fs.protected_symlinks`, `fs.protected_hardlinks`,
  `fs.protected_regular`, `fs.protected_fifos` без их изменения.
- [ ] Учитывать ro/nosuid/nodev/noexec, существующие открытые дескрипторы,

- [ ] Не путать проверку доступа с разрешением ядра: не строить безопасность
  на последовательности `access` → открытие или только на арифметике mode.

### fstab: обязательные нюансы реализации

Исследовано по [fstab(5)](https://man7.org/linux/man-pages/man5/fstab.5.html),
[libmount](https://www.kernel.org/pub/linux/utils/util-linux/v2.41/libmount-docs/libmount-Table-of-filesystems.html),
[systemd.mount](https://www.freedesktop.org/software/systemd/man/latest/systemd.mount.html)
и [systemd-fstab-generator](https://www.freedesktop.org/software/systemd/man/latest/systemd-fstab-generator.html).
Локально подтверждено на util-linux 2.39.3: повреждённая строка перед правильной
даёт findmnt status 0, JSON только правильной записи и parse error в stderr.

- [x] Чтение через штатный libmount: parser stderr и неполное число записей
  отклоняют частичный результат даже при status 0; смешанный valid/invalid
  файл проверен тестом.
- [x] Ограниченный снимок обычного файла; лимиты входа/строки/числа записей,
  таймаут утилиты, удаление приватного временного снимка и plan без чтения.
- [x] Сохранить исходный порядок записей; не сортировать и не превращать
  повторные target в словарь. Дубликат может требовать разъяснения намерения,
  а несколько swap с `none` не означают конфликт mountpoint.
- [x] Libmount корректно разбирает `\040`/`\011`/`\134` и кавычки,
  без shell lexer для полей. На фикстурах проверены LABEL/UUID/PARTUUID,
  комментарии, пустой файл и пропущенные необязательные поля.
- [x] Опции — не обычный Split по запятой: значения вроде SELinux context
  могут содержать запятые в кавычках; повторные опции и порядок сохраняются.
  Неизвестные опции не удалять и не объявлять корректными без проверки потребителя.
- [x] Отчёт не должен раскрывать пароли/credential values из сетевых источников
  и options; хранение снимка на диске только приватное и временное.

Принятые границы:

- Чтение синтаксиса, диагностика конфигурации и проверка активного mount —
  разные результаты. `findmnt --verify` также проверяет usability; чтение
  fstab не считается проверкой boot.
- Проверка mount из fstab поддерживает целую ФС с UUID/PARTUUID и явным типом.
  Path/LABEL, swap, auto/список типов, bind/rbind, loop, move/remount и subvolume
  отклоняются; несколько активных mount в одной точке не разрешаются выбором первого.
- `nofail` не доказывает готовность backup. `noauto` не отключает
  `x-systemd.automount`; ни один из этих флагов не разрешает пропустить
  проверку активной ФС. Читающий разбор не обходит target, а проверка mount
  сначала читает таблицу ядра без канонизации.
- Systemd трактует passno как boolean с root-first проверкой; традиционное
  fsck ordering не переносится на generator. Учитываются как ограничения,
  а не как реализованная модель зависимостей systemd.
- Запись `/etc/fstab`, `mount -a`, daemon-reload и systemd generator на хосте
  не входят в этот интерфейс и не запускались его тестами.

Остаётся проверить или реализовать:

- [ ] Эффективные mount options, доступ для записи и свободное место как
  отдельные требования; успешный identity/type check их не подтверждает.
- [ ] Специализированные проверки bind/rbind, swap, сетевых ФС, псевдо-ФС,
  btrfs subvolumes и automount; не разрешать каждую source как block device.
- [ ] Диагностика зависимостей systemd: `_netdev`, nofail/automount,
  native units, initrd и kernel command line, без изменения системы.
- [ ] Реальные GPT/PARTUUID и отдельный backup-mount; текущий WSL-тест
  использует искусственный fstab и настоящий root ext4, не backup/restore.
- [ ] Настоящий automount: подтвердить отсутствие непреднамеренной активации;
  сейчас проверены порядок запросов и autofs-only отказ на подменённых утилитах.
- [ ] Mount/umount, сетевые ФС и boot — только отдельный стенд с положительным
  и отрицательным сценариями; обычные тесты не меняют конфигурацию хоста.

## SSH и резервное копирование

и восстановление — только отдельная тестовая VM.

- [ ] Для каждой операции показать выигрыш yesh в читаемости: список узлов,
  явные источники/назначения, проверка перед действием, видимая ошибка.
- [x] Базовые read-only SSH health и SCP argv проверены на подменённых утилитах;
  ключи/пароли в yesh-код не попадают, порт и timeout видны явно.
- [ ] Не читать и не хранить приватные ключи, пароли и passphrase; использовать
  обычный `ssh`/`ssh-agent`/`~/.ssh/config`, не подменять хранилище учётных
  данных.
- [ ] SSH: типизированный узел, явный порт/пользователь, timeout и host-key
  policy; запрещать молчаливый `StrictHostKeyChecking=no` и shell-код на узле.
- [ ] SCP: передача одного файла/списка файлов с проверкой локальных путей,
  назначения и частичного результата; не раскрывать секреты в argv/журнале.
- [ ] rsync: `--dry-run`/preview до записи, явный источник и назначение,
  отсутствие неявного `--delete`, проверка mount и свободного места; отдельно
  различать exit code и предупреждения.
- [x] rsnapshot: `configtest`, lock conflict, две ротации, retention и
  hard-link snapshots проверены локальным примером и интеграционными тестами.
- [ ] rsnapshot: mount/source check и свободное место перед ротацией.
- [ ] pv: отделять progress/stderr от двоичных данных, ограничивать pipeline,
  проверять завершение всех стадий и не считать показанный счётчик успехом.
- [ ] Общий `--plan` и отчёт: какие узлы, пути, команды, объём и изменения
  будут затронуты; в плане не выполнять внешние команды.
- [x] Р.П.П.: локальный стенд, обрыв передачи, lock, повторный запуск и
  проверка восстановления.
- [ ] Р.П.П.: отдельные host-key/timeout, заполненное место,
  незамонтированный backup-диск и тестовый SSH-сервер.

## Реальные практические примеры

- [x] SSH health и SCP: runnable-примеры, проверка argv, host-key policy,
  отказ при отсутствующем локальном source; локальная loopback-передача через
  реальный SSH/SCP выполнена и сверена побайтно. Копирование на отдельную
  удалённую машину и restore пока не заявляются.

- [x] [Р.П.П.](practical-examples.ru.md) как исполняемые `.yesh`-файлы и Go-тесты.
- [x] Архив tar/gzip: восстановление и сравнение байтов, пробелы/двоичные данные,
  JSON-отчёт; ошибка не публикует незавершённый результат.
- [x] Конфигурация: предварительная проверка, права `0640`, сохранение рабочей
  версии при отказе; проверка примера не заменяет штатный валидатор приложения.
- [x] Deploy/службы: проверка argv, порядка действий и остановки через тестовые
  SSH/systemctl; реальное удалённое управление не выполняется.
- [x] rsync: реальный предварительный просмотр без записи, копирование,
  сохранность источника и лишних файлов назначения без неявного `--delete`.
- [x] pv: реальная передача двоичных данных, прогресс в stderr отдельно от данных.
- [x] rsnapshot: configtest, две ротации, старое/новое содержимое,
  повторное использование hard links и освобождение lock.
- [x] Отмена задания: завершение группы, сохранение частичного результата,
  отсутствие готового файла и ложного успешного состояния.
- [x] При отсутствии утилиты назвать требуемый пакет; не выдавать пропуск за успех.
- [ ] Backup реального mount: проверка source/UUID, свободного места,
  отказ при незамонтированном диске; только в отдельной тестовой среде.
- [ ] Реальный SSH/systemd и восстановление после сбоя машины в отдельной VM.

## Длительные операции и файлы состояния

Согласованный первый шаг отложен пользователем; сейчас не реализовывать.

- [ ] Параметр CLI `yesh --command-timeout 30m backup.yesh`, без нового
  синтаксиса языка. Предел действует отдельно на каждую команду или конвейер,
  а не на весь скрипт; значение по умолчанию — пять минут.
- [ ] Отклонять нулевую, отрицательную и неверно записанную длительность.
- [ ] Передавать настройку из CLI в существующий runtime отмены; показывать
  бюджет в `--plan` и сообщать о его превышении с файлом и строкой.
- [ ] Проверить обычное завершение, превышение времени, TERM→KILL и ожидание
  группы; в Р.П.П. прерванный backup не публикует готовый результат.
- [ ] Обновить обе man-страницы yesh(1), документацию и статус TODO.
  Новые библиотеки и привилегии для этого шага не нужны.

Общий срок скрипта, ожидание блокировки и предел отсутствия прогресса —
следующие отдельные настройки, не скрытые значения `--command-timeout`.
Проверка текущего runtime подтверждена Go 1.27.3 на Rocky Linux 9.8. Сам
`--command-timeout` остаётся
отложенным и ещё не реализован; ранние проверки с временным modfile для Go
1.22.2 не заменяют проверку нового интерфейса.

- [x] [Проектирование](long-running-and-state.ru.md): время выполнения,
  прогресс, события, снимок состояния и прикладная точка возобновления.
- [ ] Явные бюджеты ожидания lock, выполнения, отсутствия активности,
  общего задания и освобождения ресурсов. Сейчас пять минут на конвейер фиксированы.
- [ ] Наблюдаемое задание с ID и владельцем; отмена учитывает backend,

## POSIX и переносимость

BusyBox упоминался как пример набора системных команд, а не как цель
интеграции. Отдельный профиль BusyBox/rescue и собственный набор замен
Unix-утилит в текущий план не входят.

- [ ] Проверять наличие внешних системных команд и нужных возможностей;
  при отсутствии явно указывать требуемую утилиту и пакет.
- [ ] Проверять применяемые опции по локальным man и возможностям реализации;
  различия системных утилит не должны менять смысл скрипта молча.
- [x] Рабочее WSL/Linux-окружение для интеграционных тестов
  (ограничения: [отчёт](linux-integration.ru.md)).
- [ ] В WSL подтвердить доступ к systemd, cgroup v2, `/proc` и `/sys`.
- [ ] В WSL установить/проверить procps, kmod, udev, util-linux,
  tmux, screen, rsyslog и средства чтения journal.
- [x] В Linux CI запускать проверки групп процессов, SIGPIPE,
  ограничения времени и файловых дескрипторов.
- [ ] Отдельно пометить тесты, требующие root, CAP_SYS_ADMIN или реального устройства.
- [ ] Условия сборки для Linux: `/proc`, pidfd, cgroup, systemd и kmod.
- [ ] Не считать Windows/WSL полной POSIX-проверкой без указания ограничений.
- [ ] Интеграционные Linux-тесты с управлением cgroup v2/systemd.
- [ ] **Отложено пользователем:** macOS/Darwin. Новую работу и проверки
  этого направления пока не начинать; результаты Linux/WSL не переносить
  на Darwin автоматически. Существующая кросскомпиляция не доказывает выполнение.
- [ ] Резервная реализация Windows без обещания POSIX-управления заданиями.
- [ ] TTY, активная группа процессов терминала и PTY — после первой версии,
  с отдельными ограничениями безопасности.
- [ ] Проверить ввод с реального терминала: наследование stdin само по себе
  не передаёт новой группе право чтения TTY и не исключает SIGTTIN.
- [ ] `cd`, окружение, `export` и рабочий каталог как встроенные операции.
