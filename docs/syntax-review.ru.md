# Стройность синтаксиса и декларативные удобства

Статус: принятое правило разрешения имён и направления развития.

## Что сохраняем

Обычные команды Unix, байтовые каналы `|`, перенаправления, блоки с `:`
и отступами, строки отдельно от списков, ошибка по умолчанию останавливает
выполнение. Это достаточная основа для административных скриптов.
Предметные операции не должны превращать каждую утилиту в новую грамматику.

Значение переменной всегда запрашивается явно:

```yesh
service = api
echo $service
# api
echo service
# service
```

Правило: `$name` раскрывает только существующую переменную; неизвестное или
неверное `$`-имя — ошибка. Обычное слово и слово в кавычках всегда буквальны.
Поэтому добавление присваивания не меняет смысл ранее написанной команды.
Единственная форма подстановки — `$name`; `${name}` намеренно не поддерживается.

## Проверенные ошибки реализации

- Строка `"a\nb"` раньше давала перевод строки в присваивании, но `anb`
  в аргументе команды. Теперь используется одно декодирование кавычек.
- `["a,b", "c"]` раньше делился на три элемента. Разделитель теперь
  учитывает кавычки и вложенность; вложенные списки по-прежнему запрещены.
- Разбор `for` сжимал пробелы внутри строк. Исходный текст значения теперь
  сохраняется; отступы с табуляцией отклоняются.

Эти исправления и явное разрешение имён проверяются `values_test.go`.

Остальные подтверждённые проблемы:

- В старом `examples/deploy.yesh` слова `release/` и `host:target/`
  передавались буквально. Подстановка внутри слова не реализована;
  адрес и путь нужно пока задавать полным отдельным значением.
- `echo`, `true`, `false` встроены только в простой форме; с перенаправлением
  или в конвейере выбирается внешняя команда. Нужна единая модель встроенных
  операций, а не скрытое переключение из-за появления `|`.

В очередном шаге полировки устранены два пункта: используется только
`exists path`, старое написание со скобками получает подсказку; `exit code`
теперь является встроенной управляющей операцией с явным кодом 0..255.
Условия разобраны в AST по словам с учётом кавычек: строка с `matches`
не становится оператором. Отказ доступа при exists больше не скрывается
под false. Правила и ошибки: [условия и завершение](control-flow.ru.md).

## Что брать из других оболочек

YSH отдельно описывает язык командных слов и подстановки выражений,
включая раскрытие списка. Полезен сам явный переход между значением и argv,
а не всё множество его синтаксических форм.
[YSH word language](https://github.com/oils-for-unix/oils/blob/master/doc/ref/chap-word-lang.md).

Nushell требует явного раскрытия списка в аргументы внешней команды и
умеет отдельно выбирать встроенную и внешнюю команду. Это полезные
контрольные примеры для списка и разрешения имён; переносить новые знаки
в yesh из этого не следует.
[Nushell: external commands](https://www.nushell.sh/book/running_externals.html).

Fish избегает разбиения строки по пробелам при раскрытии переменных,
но его переменные имеют списочную семантику. Для yesh сохраняем различие
между строкой и списком, не копируя всю модель fish.
[fish: variable expansion](https://fishshell.com/docs/current/language.html#variable-expansion).

## Полезные декларативные свойства

Здесь нужны три свойства, а не отдельный язык конфигурации.

1. **Проверяемые требования.** Уже намеченное `require mounted /mnt/backup`
   должно проверять условие и останавливать работу с понятной причиной,
   не создавать каталог и не монтировать устройство молча. Дополнительно
   полезны требования к доступности команды, окружению и свободному месту.
2. **Желаемое состояние небольшой области.** Известный файл имеет конкретные
   права и владельца; пакет установлен в заданной версии; служба запущена.
   Повторная проверка без отличий ничего не меняет. Проверяем существование
   и точное состояние, а не всегда повторяем chmod/chown/install/restart.
3. **План и проверка изменения.** Показать текущее и желаемое состояние,
   стоимость и побочные действия, затем применить явно и проверить результат.
   Если состояние изменилось после плана, остановиться или построить новый план.

У systemd полезно различение условия пропуска и обязательной проверки:
неуспешное Assert делает запуск задания ошибкой, тогда как Condition может
пропустить запуск. Для нашего `require` нужен явный отказ, особенно перед backup.
[systemd.unit](https://www.freedesktop.org/software/systemd/man/257/systemd.unit.html).

У Ansible полезны проверка без применения и сравнение изменений. Руководство
оговоривает поддержку проверки конкретным модулем и её ограничения. В yesh
неподдерживаемый план должен быть явно отмечен; нельзя обещать будущий
результат произвольной Unix-команды по одному её имени.
[Ansible: check and diff](https://docs.ansible.com/projects/ansible-core/devel/playbook_guide/playbooks_checkmode.html).

NixOS показывает удобство описания желаемой конфигурации системы. Для yesh
масштаб намеренно меньше: конкретные ресурсы одного скрипта, а не
владение всей машиной и её графом конфигурации.
[NixOS manual](https://nixos.org/manual/nixos/stable/).

## Порядок работы

Сначала единые значения, кавычки, списки, диагностика и встроенные `cd` /
окружение / завершение. Затем требования к выполнению. После этого —
небольшие операции над состоянием с проверяемыми последствиями:
[права файлов](permissions.ru.md), [пакеты](packages.ru.md), службы и монтирование.

Пока не нужны неявные перезапуски по уведомлениям, общий граф зависимостей,
ленивые вычисления, каскад переменных из десятка источников и второй язык
шаблонов. Изменённый файл сам по себе не даёт разрешения перезапустить службу.
