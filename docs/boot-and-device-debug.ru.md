# Initramfs и диагностика устройств

Это полезный отдельный профиль yesh: «почему устройство не работает?»

## Две разные задачи

### Сборка initramfs

`dracut` и `mkinitcpio` работают до перезагрузки и создают образ ранней
userspace-системы. Они не являются одинаковыми интерфейсами:

- dracut использует модули, drivers, hostonly-режим и конфигурацию;
- mkinitcpio использует `MODULES`, `BINARIES`, `FILES` и упорядоченные `HOOKS`;
- порядок hooks и выбранный kernel version влияют на результат.

Поэтому yesh должен иметь общий intent, но отдельные backend-адаптеры:

```yesh
initramfs for kernel 6.12.1:
    root by uuid "..."
    driver nvme
    driver xfs
    hook udev
    filesystem xfs
    build /boot/initramfs-6.12.1.img
```

Backend dracut может использовать `--add-drivers`, `--add`, `--kver`,
`--force` только после явного подтверждения. Backend mkinitcpio должен
генерировать проверяемый config/preset с `MODULES`, `FILES` и `HOOKS`, а не
пытаться преобразовать dracut-модули один в один.

Официальные интерфейсы: [dracut usage](https://github.com/dracut-ng/dracut/blob/main/man/dracut.usage.adoc),
[mkinitcpio manual](https://man.archlinux.org/man/core/mkinitcpio/mkinitcpio.8.en).

### Диагностика загруженной системы

```yesh
diagnose device /dev/nvme0n1
```

Read-only preflight должен собрать:

1. `dmesg` по уровню и времени, без бесконечного `--follow`;
2. `udevadm info` и свойства устройства;
3. `lsblk`, `blkid`, `findmnt`;
4. kernel version и наличие `/lib/modules/<kver>`;
5. `lsmod`, `modprobe -n -v` и зависимости;
6. ошибки I/O, firmware, filesystem и mountpoint;
7. diff dmesg до/после диагностического действия.

`udevadm` официально предоставляет `info`, `settle`, `monitor`, `test` и
`wait`, поэтому ожидание появления устройства должно быть конечным `wait ...
within`, а не sleep-loop. [udevadm](https://www.freedesktop.org/software/systemd/man/262/udevadm.html)

## Работа с kernel modules

Целевой синтаксис:

```yesh
module = kernel module nvme
show module
load module
verify module loaded
```

Безопасная реализация:

- сначала `modprobe -n -v` и проверка `/lib/modules/<kver>`;
- затем явный `modprobe`;
- после загрузки проверка `/sys/module/<name>` и `lsmod`;
- чтение новых сообщений `dmesg`;
- `unload` запрещён, если модуль используется, и требует явного действия;
- параметры модуля не берутся из неэкранированной строки;
- имя модуля нормализуется (`-` и `_` имеют специальную совместимость
  modprobe), но показывается пользователю в исходном и kernel-виде.

`modprobe` сам разрешает зависимости через `modules.dep.bin`, а ошибки
загрузки часто дополнительно объясняются сообщениями ядра в dmesg. Поэтому
один ненулевой exit status недостаточен для хорошей диагностики.
[modprobe(8)](https://man7.org/linux/man-pages/man8/modprobe.8.html)

## Анти-мартышка

- `dmesg --follow`, `udevadm monitor` и бесконечные retry запрещены в MVP;
- `dracut --force` и замена существующего initramfs требуют явного `apply`;
- перед заменой сохраняются checksum, owner, mode и backup старого образа;
- kernel version всегда видна в плане;
- hostonly-образ предупреждает о непреносимости на другой контроллер/машину;
- после сборки проверяются содержимое образа (`lsinitrd`/`lsinitcpio`), драйверы,
  filesystem и root UUID;
- `modprobe -r`, `rmmod`, `mkinitfs` и запись в `/boot` не выполняются скрыто;
- любой диагностический отчёт должен отделять «устройство не видно»,
  «драйвер не загружен», «драйвер загружен, но firmware/IO ошибочны» и
  «filesystem/mount сломан».

## Практическая ценность

Это не универсальная абстракция над Linux. Ценность — в повторяемом runbook:
yesh показывает, что проверяет, строит план, делает безопасные read-only
проверки, затем выполняет только явно разрешённое действие и сохраняет
диагностический diff. Такой сценарий полезен для серверов, rescue-образов,
драйверов хранения, сетевых карт и проблем после обновления kernel.

## Р.П.П.: модуль для устройства и проверка initrd

Статус этого раздела — проектирование диагностики. Готового встроенного
`diagnose device` пока нет. На первом этапе не загружаем и не выгружаем модули,
не запускаем rebuild и не заменяем файлы в `/boot`.

### Цепочка доказательств

1. Указать устройство и роль: нужно ли оно для корневой файловой системы
   до её монтирования или допустима загрузка драйвера позже.
2. Разрешить sysfs/udev-идентичность и `modalias`; получить все подходящие
   модули и фактическую привязку драйвера. Для устройства без `/dev`-узла
   начинать с PCI/USB/sysfs, а не делать вывод «устройства нет» по lsblk.
3. Различать встроенный драйвер, загруженный модуль и только имеющийся
   на диске `.ko`. Проверять `modules.builtin`, `modules.alias`, зависимости,
   текущую привязку драйвера и доступные данные, а не только вывод lsmod.
4. Явно выбрать версию целевого ядра и соответствующий образ initrd.
   Текущий `uname -r` и ядро следующей загрузки могут различаться.
   Наличие образа в `/boot` не доказывает, что загрузчик выбрал именно его.
5. Получить манифест образа штатным инструментом и проверить модуль,
   зависимости, нужную firmware и данные раннего userspace. Учитывать
   сжатые `.ko.xz` / `.ko.zst` и совместимость версии ядра.
6. Для root-устройства проверить всю цепочку: контроллер, транспорт,
   RAID/LVM/шифрование при наличии, файловая система, разрешение UUID/PARTUUID.
   Одного найденного `nvme.ko` недостаточно для обещания успешной загрузки.

Встроенный драйвер не требует отдельного `.ko` в initrd. И наоборот,
файл модуля внутри образа не доказывает подходящий alias, возможность
проверки подписи, доступность firmware или успешную инициализацию устройства.
Поддержка firmware, Secure Boot/lockdown, blacklist и soft dependencies
должна отражаться отдельными фактами, а не общим «модуль есть».

### Что можно вызвать как внешние читающие команды

```yesh
module = "nvme"
uname -r
modinfo -F filename module
modinfo -F depends module
modinfo -F firmware module
modprobe -n -v module
```

Сравнение с Bash: те же команды с `"$module"` и `set -euo pipefail`.
Правило: dry-run показывает план modprobe, но не подтверждает загрузку.
Пример рассчитан на наличие метаданных модуля для текущего ядра; их отсутствие
останавливает выполнение с ошибкой и требует разбора, а не принудительной загрузки.
`modprobe --resolve-alias` и `--show-depends` полезны для будущего адаптера,
но их вывод нужно разбирать с учётом версии kmod и директив install/softdep.
[modprobe.d(5)](https://man7.org/linux/man-pages/man5/modprobe.conf.5.html).

Просмотр конкретного подготовленного образа:

```yesh
image = "/path/to/test-initrd"
lsinitramfs image
```

Сравнение с Bash: `lsinitramfs "$image"`.
Правило: инструмент просмотра выбирается по формату и установленному набору
initramfs, а образ задаётся явно. Для dracut используется lsinitrd,
для mkinitcpio — lsinitcpio; это не повод устанавливать все сборщики сразу.
В Ubuntu для lsinitramfs нужен пакет `initramfs-tools-core`.

Нужен контроль возможностей для многосегментных образов, раннего microcode
и UKI; ошибку или неполный разбор нельзя превращать в «модуль отсутствует».
Не извлекать недоверенный архив в текущий каталог и не печатать содержимое
crypttab, ключей и credential-файлов в общий отчёт.
[lsinitramfs(8)](https://manpages.debian.org/unstable/initramfs-tools-core/lsinitramfs.8.en.html),
[lsinitcpio(1)](https://man.archlinux.org/man/core/mkinitcpio/lsinitcpio.1.en).

### План Go-проверок

Первый реальный набор уже добавлен: `TestLinuxPracticalInitrdModuleManifest`
создаёт newc через cpio, сжимает gzip/zstd и вызывает установленный lsinitramfs
через yesh. Он проверяет пять случаев манифеста с фиктивным содержимым `.ko`;
ядро, `/boot` и привязка настоящего устройства не изменяются.

На сохранённых манифестах и искусственном sysfs проверять:

- встроенный драйвер без `.ko`: не выдавать ложную ошибку;
- модуль есть на диске, но отсутствует в выбранном образе;
- основной модуль есть, зависимость или firmware отсутствует;
- модуль для другого ядра или несколько подходящих alias;
- образ не читается, повреждён, имеет неподдерживаемый формат или неполный манифест;
- отсутствует утилита просмотра: назвать нужный пакет, не угадывать результат;
- установленный модуль не привязан к устройству, ошибка firmware/IO отдельно;
- запрет изменения в плане: не выполнены load/unload/rebuild и запись `/boot`.

Проверка реальной загрузки и root-устройства — отдельная одноразовая VM
с известным ядром/образом и серийной консолью. Успех таких испытаний нельзя
заменить Windows-тестом, чтением каталога WSL или одним сравнением имени `.ko`.
